## Abstract

FML is a declarative, text-based language for describing **multidimensional
financial planning and analysis models**: the dimensions a business is analysed
by, the relationships between those dimensions, and the variables that hold
inputs, imported actuals, calculations and reported outputs. A model written in
FML is a set of plain-text documents. It can be read by a person, reviewed in a
pull request, diffed, generated by a program, and loaded into a conforming
modeling engine.

This document defines the lexical structure, syntax, static rules and
evaluation semantics of FML 1.0. Two companion documents build on it: the
[FML Modelling Guide](fml-modelling-guide-1.0.md) (informative) — the practices
that make a model correct, fast and maintainable, with particular attention to
the design of dimensions — and the
[FML Agent Authoring Protocol](fml-agent-protocol-1.0.md) — the procedure that
automated agents follow when they generate or modify FML models. They are cited
here as "Guide §n" and "Protocol §n".

## 1. Introduction

### 1.1 Purpose

Financial planning models are, structurally, a small number of things repeated
at scale: a set of business axes (accounts, entities, cost centres, products,
employees, periods, scenarios), a set of quantities measured along subsets of
those axes, and rules that derive some quantities from others. Spreadsheets
express this implicitly, through cell positions. FML expresses it explicitly:

```fml
# Two business axes, one relationship between them
dimension Product from "dimensions/Product.csv"
  @parent Category
dimension Category from "dimensions/Category.csv"

# Planner inputs
"Sales Volume IN" { Product, Versions, YearMonth }
"Sales Price IN"  { Product, Versions, YearMonth }
  @rollup average

# A calculation, written once, valid for every product, version and month
"Sales Revenue" { Product, Versions, YearMonth } = "Sales Volume IN" * "Sales Price IN"
  @readonly true
```

The formula `"Sales Revenue" = "Sales Volume IN" * "Sales Price IN"` is stated
once and holds at every coordinate of its grain. Revenue by `Category`, by
quarter or by year is not written at all: it is obtained by aggregation along
the declared dimension graph.

### 1.2 Design goals

FML is designed to be:

1. **Declarative.** A document states *what* the model is, never the order in
   which to compute it. Dependency order is derived by the engine.
2. **Dimensional.** Every quantity is declared together with the axes it varies
   by (its *grain*). Aggregation follows from the grain and the dimension
   graph; it is not hand-written.
3. **Variable-centric.** Formulas belong to variables, not to cells. One
   formula governs every cell of its variable.
4. **Sparse by default.** Absence of data is a first-class state (*null*),
   distinct from zero, and costs nothing to store.
5. **Minimal in syntax.** The language has three kinds of statement. Modeling
   opinions (naming, layering, graph shape) are expressed as conventions and
   enforced by linters, not baked into the grammar.
6. **Text-first and diffable.** Documents are line-oriented UTF-8 text with a
   canonical form, suitable for version control and code review.
7. **Machine-authorable.** The grammar is small and regular, and the Agent
   Protocol gives automated agents a procedure for producing reviewable models.

### 1.3 Scope

This specification defines:

- the textual syntax of FML documents and of the dimension member files that
  accompany them;
- the static rules a well-formed model satisfies;
- the evaluation semantics a conforming engine implements;
- the standard function library;
- the diagnostics a linter reports, including those that check the Modelling
  Guide's rules (Annex C).

This specification does **not** define:

- presentation artefacts — input forms, reports, dashboards or sheets that
  display variables. These are separate artefacts that *consume* an FML model;
- data integration — how actuals are extracted from source systems and written
  into variables;
- access control, workflow, approval or audit trails;
- the wire format used by any particular engine, and the properties, `@rollup`
  values and functions an engine adds beyond this specification — those are
  documented in its implementation profile (§2.5, Annex D).

FML does carry **presentation and entry metadata** — `@format`, `@decimals`,
`@numberFormat`, `@folder`, `@desc`, `@readonly`, `@numberValidation` and the
dimension folder directive. A processor preserves it (§5.5); it has **no
evaluation meaning**, and how an engine displays it or enforces it at entry is
implementation-defined.

### 1.4 Relationship to the reference implementation

FML originated as the text format of the Farseer modeling platform, which is
the reference implementation of this specification. Section 11 defines the
evaluation semantics; every rule in it is stated so that a second engine can
implement it without reference to Farseer. Farseer's choices where this
document leaves a behaviour implementation-defined, its error messages and its
known deviations are recorded in its implementation profile.

Farseer also accepts constructs that are tied to how it stores, enters and
computes values — calculation and activation flags, top-down entry, measures,
a `formula` rollup, growth functions. They are not part of FML. They are
documented as Farseer **extensions** in the
[Farseer Implementation Profile](fml-farseer-profile-1.0.md) (§2.5, Annex D).

### 1.5 How to read this document

- Readers who want to **write models** should read Section 3, skim Sections
  4–9, read Sections 10–11 carefully, and then read the Modelling Guide.
- Readers who want to **implement a parser or linter** need Sections 4–9,
  Section 15, Annex A and Annex C.
- Readers who want to **implement an engine** need all of this document.
- **Automated agents** should read Section 3, Section 11 and the Agent Protocol
  in full, and use the remainder as reference.

Rules that carry an identifier in brackets — for example **[EVAL-4]** — are
the load-bearing rules of the specification. Identifiers are stable across
minor versions and may be cited in diagnostics, reviews and tooling.

## 2. Conformance

### 2.1 Notational conventions

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHALL NOT**,
**SHOULD**, **SHOULD NOT**, **RECOMMENDED**, **NOT RECOMMENDED**, **MAY** and
**OPTIONAL** in this document are to be interpreted as described in BCP 14
(RFC 2119, RFC 8174) when, and only when, they appear in all capitals.

Grammar productions are written in the EBNF notation defined in Annex A.1.
Code blocks labelled `fml` contain FML source text. Text in a code block
following `→` describes a result, not source.

Examples omit `@readonly`, `@notes` and `@folder` for brevity unless the
property is the subject of the example; the Modelling Guide's examples set them
(Guide §2).

Examples, notes and sections labelled *informative* are not normative. All
other text of this document, Annexes A and C included, is normative.

### 2.2 Conformance classes

This specification defines five conformance classes.

| Class | A conforming member of this class… |
|---|---|
| **FML document** | satisfies the syntax of Sections 4–10 and Annex A, and the static rules of Section 15 marked *error*. |
| **FML processor** | parses every conforming document, rejects every document that violates a syntax rule with a diagnostic (Annex C), and preserves the information content of a document across a parse → emit → parse cycle (§5.6). |
| **FML engine** | is a processor that additionally evaluates models according to Sections 11–13. |
| **FML linter** | is a processor that reports the diagnostics of Section 15 under a declared profile (§15.4). |
| **FML authoring agent** | is a program that produces or modifies FML documents and follows the [FML Agent Authoring Protocol](fml-agent-protocol-1.0.md). |

A processor MAY accept syntax beyond this specification (extensions) provided
that every conforming document is still interpreted as specified, and that it
can report the use of an extension on request (§2.5).

### 2.3 Implementation-defined behaviour

Where this specification says a behaviour is **implementation-defined**, a
conforming engine MAY choose the behaviour but MUST document it. Conforming
documents SHOULD NOT depend on implementation-defined behaviour.

### 2.4 Unspecified behaviour

Where this specification says a behaviour is **unspecified**, conforming
documents MUST NOT depend on it, and engines need not document their choice.

### 2.5 Extensions and implementation profiles

**[EXT-1]** An implementation MAY define **extensions**: properties, `@rollup`
values, functions, dimension-table columns and variables with an empty grain
beyond this specification. It MUST document each
extension, and its choice for every implementation-defined behaviour (§2.3), in
an **implementation profile**. An extension MUST NOT change the meaning of any
construct this specification defines.

**[EXT-2]** A processor MUST accept a call to a function it does not recognise
(`FML-I0408`) and an `@rollup` value it does not recognise (`FML-I0905`), and
MUST preserve both across a round trip, as it does an unknown property
[PROP-12]. An engine asked to evaluate a variable that uses an extension it does
not implement MUST report it (`FML-E0409`) and MUST NOT evaluate the call as
null.

**[EXT-3]** A document that uses an extension is an FML document **with
extensions**: it is portable only to engines that implement the profile that
defines the extension. A linter MUST be able to report every use of an
extension it recognises (`FML-I0904`). Documents SHOULD use the standard
construct wherever one expresses the same thing.

**[EXT-4] (names of extensions)** The extension names of every published
implementation profile — properties, `@rollup` values, functions, dimension-table
columns, time dimensions — are listed in Annex D. Later versions of this
specification do not give a listed name another meaning. An implementation
profile's own diagnostics use a prefix of their own, never `FML-`.

Annex D lists the published implementation profiles.

### 2.6 Security and privacy considerations

FML documents and member files are data. A processor MUST NOT execute anything
a document contains, and MUST treat names, `@notes` and other text as text: a
tool that writes them into another format — a spreadsheet, a web page, a
query — escapes them for that format (in a spreadsheet, text that begins with
`=`, `+`, `-` or `@` is written as text, never as a formula). An engine SHOULD
bound the work a formula can cause before computing it [EVAL-31], so that a
model cannot exhaust it. Member files and stored values can hold personal data
— employees, salaries, customers; models that carry them are handled under the
data-protection rules that apply to that data, and examples and test material
use invented names only.

## 3. Concepts and terminology

This section defines the vocabulary used throughout the specification. Terms
are used with exactly these meanings.

**Model.** The complete set of FML documents, dimension member files and data
that together describe one planning application. Every name in a model —
dimension, variable — is resolved against the whole model.

**Document.** One FML source file (§5.1).

**Dimension.** A named, finite, ordered set of *members* along which data is
analysed — for example `Account`, `Entity`, `Product`, `Months`, `Versions`.
Dimensions are also called *dimension tables*, because each is backed by a
table whose rows are its members (§6.2).

**Member.** One element of a dimension, identified by a name unique within that
dimension — for example `"03"` in `Months`, `Plan` in `Versions`.

**System dimension.** A dimension that is predefined and managed by the
engine: `YearMonth`, `Years`, `Months`, `Quarters` and `Versions`, and
optionally `Half years` and `Year to date` (§6.7).

**Time dimension.** A dimension whose members are ordered in time and along
which the time-series functions run: the system dimensions `YearMonth`
(calendar months, such as `"2026-01"`), `Years` and `Months` (the month of the
year, a cycle of twelve), and any dimension a model declares
`@semantic time` (§6.9), such as one of days.
A grain holds at most one [VAR-9]. `Quarters`, `Half years` and `Year to date`
are **reading levels**: values are read there, never stored (§6.7).

**Parent** (also **foreign key**, **FK**). A directed relationship from a
*child* dimension to a *parent* dimension, declared by `@parent` and assigning
to each child member zero, one or several parent members (§7). The set of all
parents is the **dimension graph**.

**Grain.** The ordered list of dimensions that qualify a variable, written in
braces after its name. A variable holds at most one value for each combination
of members of its grain dimensions.

**Coordinate.** A tuple that names one member of every dimension of a grain.

**Cell.** A coordinate of a variable together with the value stored or computed
there. A cell either **exists** and holds a value, or **does not exist**.

**Null.** The state of a coordinate at which no cell exists. Null is not a
value; in particular it is not zero (§11.2).

**Variable.** A named quantity with a grain, an optional formula, and
properties (§8). Variables are the unit of definition in FML.

- An **input variable** has no formula; its cells are written by people or
  integrations.
- A **calculated variable** has a formula; its cells are computed.

**Formula.** The expression on the right-hand side of `=` in a variable
declaration. It defines the variable's value at every coordinate of its grain
(§10, §11).

**Operand.** A variable reference, literal or function call appearing in a
formula.

**Property.** A named annotation of a variable, written on a line beginning
with `@` (§9).

**Rollup.** The rule by which a variable's values are combined when a consumer
reads it at a coarser grain than its own — along a dimension that the consumer
does not carry, or from child members to a parent member (§9.4.2, §11.4, §11.6, §11.10).

**Pinned member.** A member fixed in a variable's grain with `Dim = Member`,
which places the variable's cells on that single member (§8.4).

**Filter.** A member reference passed to an aggregation function, restricting
which cells are read, for example `sum(Revenue, Region > "North")` (§11.8).

**Analytic level / synthetic level.** Informal terms for the fine-grained
dimension at which data is held (for example a chart of accounts) and the
coarser, reporting-oriented dimension it maps to through a parent (for example
statement lines). See Guide §3.3.

**Carrier.** A variable that is present (non-null) exactly where a calculation
should produce cells, used in value position to give a formula its cell domain
(§11.3, Guide §5.4).

**Engine.** A program that evaluates an FML model (§2.2).

## 4. Lexical structure

### 4.1 Source text

An FML document is a sequence of Unicode characters encoded in **UTF-8**. A
byte-order mark at the start of the document MUST be ignored. Processors MUST
accept both LF (U+000A) and CR LF (U+000D U+000A) as line terminators and MUST
treat them identically.

FML is **line-oriented**: a line terminator ends a statement, a property line
or a comment, except where §4.9 permits a construct to continue onto the next
line.

### 4.2 Whitespace

Space (U+0020) and horizontal tab (U+0009) are whitespace. Whitespace separates
tokens and is otherwise insignificant. Indentation carries no meaning;
conventionally, property lines are indented by two spaces (§5.6).

### 4.3 Comments

A comment begins with `#` or with `//` and extends to the end of the line.

```fml
# A full-line comment
Revenue { Product, YearMonth } = Units * Price   # an end-of-line comment
// Also a comment
```

A `#` or `//` inside a quoted string (§4.5) is part of the string and does not
begin a comment. Comments are not part of the information content of a
document and need not survive a round trip (§5.6).

> **Note.** Because `/` is the division operator, write `A / B` with spaces, or
> at least never `A //B`; the latter begins a comment.

### 4.4 Tokens

The lexical grammar produces the following tokens:

| Token | Form | Examples |
|---|---|---|
| *identifier* | a letter or `_`, followed by letters, digits or `_` (ASCII) | `Revenue`, `PL_Analytics`, `M12`, `_tmp` |
| *string* | characters enclosed in double quotes, with escapes (§4.6) | `"Sales Volume IN"`, `"P&L/Revenue"` |
| *number* | §4.7 | `0`, `12`, `0.05`, `-3` |
| punctuator | `{` `}` `(` `)` `,` `=` `:` `@` `>` `->` | |
| operator | `+` `-` `*` `/` | |
| line terminator | §4.1 | |

`->` is a single token. Any other character outside a string or comment is a
lexical error, except that processors MUST pass through the characters of a
formula (§10) to the expression parser.

### 4.5 Names

A **name** identifies a dimension, a member or a variable. A name is written
either as an identifier or as a string:

```text
Revenue                  # identifier form
"Sales Volume IN"        # string form — required because of the space
"P&L Total"              # string form — required because of '&'
"2026 Budget"            # string form — required because it begins with a digit
```

**[LEX-1]** A name MUST be written in string form if it is not a valid
identifier — that is, if it contains a space or any character other than ASCII
letters, digits and `_`, or if it begins with a digit. A name that is a valid
identifier MAY be written in either form; both denote the same name.

**[LEX-2]** Names are written and referenced **case-exactly**. A processor
compares variable and dimension names case-sensitively. Member names, however,
are unique within their dimension **case-insensitively** [DIM-1], so `PH` and
`Ph` cannot both be members of one dimension. Authors MUST NOT create two names
of the same kind that differ only in letter case, and MUST reference every name
with the exact case of its declaration.

**[LEX-3]** The string form denotes the characters between the quotes after
escape processing. Leading and trailing spaces inside the quotes are part of
the name. Authors SHOULD NOT create names with leading or trailing spaces, and
names MUST NOT contain control characters (U+0000–U+001F), including tab
(`FML-E0205`).

The words `dimension`, `true` and `false` are reserved in the positions where the
grammar uses them (§4.8); a dimension or variable with one of these names MUST
be written in string form.

### 4.6 String escapes

Inside a string, a backslash introduces an escape sequence:

| Escape | Denotes |
|---|---|
| `\"` | a double quote |
| `\\` | a backslash |
| `\n` | line feed |
| `\t` | horizontal tab |
| `\r` | carriage return |

**[LEX-4]** A backslash followed by any other character denotes **both**
characters unchanged (the backslash is preserved). This rule exists so that
folder paths can carry an escaped separator (§9.4.6).

A string MUST be terminated on the line on which it begins; an unterminated
string is an error (`FML-E0101`). A string can nonetheless carry a line feed
through the `\n` escape.

### 4.7 Numeric literals

```ebnf
number = [ "-" ] digit { digit } [ "." digit { digit } ] ;
```

Numbers are decimal. There is no exponent notation, no thousands separator, no
leading `+` and no leading or trailing decimal point (`.5` and `5.` are not
numbers; write `0.5` and `5`).

**[LEX-5]** A `-` immediately followed by a digit, with no whitespace between
them, is part of the numeric literal. `5 -3` is therefore the two tokens `5`
and `-3`, not a subtraction. Authors MUST separate a subtraction operator from
a following digit with whitespace: `5 - 3`.

### 4.8 Keywords and reserved words

| Word | Reserved where |
|---|---|
| `dimension` | at the start of a top-level statement (§6.1) |
| `@defaults` | at the start of a top-level statement (§9.2) |
| `true`, `false` | as property values (§9.1) |

Function names (§12) are not reserved. Property names (§9) are not reserved:
an unknown property name is preserved, not rejected (§9.5).

### 4.9 Line continuation

A construct may span lines only at the following points. Everywhere else, a
line terminator ends the construct.

1. Between a variable's name and its opening `{`, and between its closing `}`
   and `=`.
2. Anywhere inside a grain `{ … }`, after `{`, after a `,`, and before `}`.
   (Processors MAY accept grain entries separated by a line break without a
   comma; canonical form always writes the comma.)
3. Anywhere inside parentheses in a formula.
4. After `=` at the start of a formula.
5. At the outermost level of a formula, when the line ends with a binary
   operator (`+ - * /`), or when the next non-blank line begins with one. A
   line beginning with a negative literal (`-3`) is not a continuation [LEX-5];
   write `- 3`.
6. Anywhere inside an object value of a property (§9.1).
7. Anywhere inside the braces of an inline member list (§6.1), after `{`,
   after a `,`, and before `}`.

**[LEX-6]** A formula ends at a line terminator, even after a trailing operator,
when the next non-blank line begins a property line (`@`), a dimension
declaration, or a variable declaration (a name followed, possibly on a later line, by `{`),
or when the end of the document is reached.

```fml
# All three forms are equivalent
Total { Entity, YearMonth } = Revenue - "Cost of sales" - "Operating expenses"

Total { Entity, YearMonth } =
    Revenue
  - "Cost of sales"
  - "Operating expenses"

Total
  { Entity, YearMonth }
  = Revenue - "Cost of sales"
  - "Operating expenses"
```

> **Note.** Processors are not required to preserve the authored line layout of
> a formula; the canonical form (§5.6) writes each formula on a single line.

## 5. Documents and models

### 5.1 Documents

An FML document contains zero or more **top-level statements**:

```ebnf
document   = { statement | blank-line } ;
statement  = dimension-declaration | defaults-block | variable-declaration ;
```

- **dimension declarations** (§6.1), each followed by its property lines;
- **defaults blocks** (§9.2) — any number; each applies to the variable
  declarations that follow it, up to the next one;
- **variable declarations** (§8), each followed by its property lines (§9).

The file extension for FML documents is **`.fml`**. An implementation profile
MAY name further extensions its tooling reads and writes.

The smallest conforming model is one dimension and one input variable:

```fml
dimension Product { P100, P200 }
"Revenue IN" { Product, YearMonth }
```

### 5.2 Models

A model is the union of all documents in a **model directory** (and its
subdirectories), together with the member files its dimension declarations
name (§6.4).

**[DOC-1]** Variable names MUST be unique across the whole model, not merely
within a document (`FML-E0201`).

**[DOC-2]** The order of documents, and the order of statements within a
document, carry no meaning — with one exception: which defaults block a
variable declaration inherits from depends on where the declaration stands
(§9.2). The engine derives evaluation order from formula references (§11.11).

**[DOC-3]** A defaults block applies only to the document that contains it. It
does not apply to other documents of the same model, whatever order the
documents are read in.

### 5.3 Declaration before use

Every dimension and every variable of a model is declared exactly once: a
dimension by a dimension declaration (§6.1), a variable by a variable
declaration (§8). The system dimensions (§6.7) are the only exception: the
engine provides them, and a model does not declare them.

**[DOC-6]** A grain, a `@parent` property, a member reference or a member file
that names a dimension which is neither declared nor a system dimension is an
error (`FML-E0208`). A dimension declared twice is an error (`FML-E0209`). A
formula reference to a name that is not a variable of the model is an error
(`FML-E0301`). **A reference never creates a dimension, a member or a variable
implicitly**: a misspelt name is reported, never added to the model.

Declaration order carries no meaning [DOC-2]: a variable may be declared before
the dimensions of its grain. Examples in this specification are fragments; the
dimensions they use are assumed to be declared.

### 5.4 Recommended layout

The following layout is RECOMMENDED. It is a convention, not a rule.

```text
model/
  variables/            # FML documents, one or more
    import.fml          # variables loaded from source systems
    inputs.fml          # planner inputs
    revenue.fml         # one document per business domain …
    workforce.fml
    statements.fml
    controls.fml
  dimensions.fml        # every dimension declaration of the model
  dimensions/           # the member files the declarations name (§6.4)
    Account.csv
    Entity.csv
```

Placing all dimension declarations in a single `dimensions.fml` makes the
dimensions and the dimension graph reviewable in one place.

### 5.5 Information content

The **information content** of a document is: the set of dimension
declarations (name, member source, inline members in order, and properties)
and the set of variable declarations (name, grain with pinned members, formula,
and properties — each variable's own together with those it inherits from its
defaults block, §9.2). Comments, blank lines, statement order once the defaults blocks are
applied, indentation, the choice between identifier and string form for a name,
the choice between stating a property on the variable and inheriting it, and
the line layout of formulas are **not** information content.

### 5.6 Canonical form

Processors that emit FML SHOULD emit the **canonical form**, which makes
emitted documents stable under version control:

1. Dimension declarations first, sorted by name, under the comment
   `# --- Dimensions ---`, with no blank line between them, each followed by
   its property lines in the order `@semantic`, `@rollup`, `@parent` (sorted by
   dimension, with `many` before `required`), `@attribute` (in the order
   written), `@null`, `@folder`, `@desc`.
2. Variable declarations next, under `# --- Variables ---`, sorted by name (or,
   optionally, grouped by folder, or in dependency order).
3. Each variable as one header line `Name { grain } = formula`, the formula on
   a single line, followed by its property lines indented by two spaces.
4. Properties in the canonical order: `@type`, `@rollup`, `@format`,
   `@decimals`, `@numberFormat`, `@folder`, `@desc`, `@notes`, `@readonly`,
   `@numberValidation`, then the properties of an
   implementation profile in the order the profile gives, then any other
   property in alphabetical order.
5. A property equal to its default (§9.4) omitted.
6. Names in identifier form where valid, otherwise string form.
7. Inside formulas: no space between a function name and `(`; no space inside
   parentheses or before `,` and `)`; one space after `,`; one space on each
   side of a binary operator and on each side of `>` in member references
   (`Dim > Member`).
8. One blank line between variable blocks.
9. No defaults blocks: every inherited property is stated on its variable
   (sorting would otherwise change what a variable inherits, §9.2).

**[DOC-4]** A conforming processor MUST satisfy, for every conforming document
`d`: `parse(emit(parse(d)))` has the same information content as `parse(d)`.

### 5.7 The model manifest

What a model needs beyond its documents and member files — the FML version it
is written in, its time horizon and its versions — is stated in a **model
manifest**: a JSON file named `model.json` at the root of the model directory.

```json
{
  "fml": "1.0",
  "horizon": { "from": "2026-01", "to": "2028-12" },
  "versions": ["Actual", "Plan", "Budget"],
  "membersComplete": true
}
```

**[DOC-5]** A model SHOULD have a manifest. Its fields:

| Field | Required | Meaning |
|---|---|---|
| `fml` | yes | the FML version the model is written in, `"MAJOR.MINOR"` |
| `horizon` | yes | the first and last `YearMonth` member of the model; both in whole years (`from` ends in `-01`, `to` in `-12`), `from` not after `to`. It defines the members of `YearMonth` and `Years` [DIM-9] |
| `versions` | no | the members of `Versions`; `Actual` and `Plan` are always members, whether listed or not |
| `membersComplete` | no | `true` when the dimension declarations define every member of every non-system dimension that has a member source: the members listed inline, the members of the member files they name, and the NULL member of each dimension declared `@null` (§6.1, §6.5). A member reference to any other member of such a dimension is then an error at the document stage (`FML-E0302`). A dimension declared with no member source has its members as data; references to its members are checked at the model stage only (§15.1). Default `false` |

A processor MUST accept and preserve fields it does not know. A manifest that
is not valid JSON, names an `fml` version the processor does not implement, or
violates the table above is an error (`FML-E0608`). Without a manifest, the
horizon and the versions are implementation-defined (§2.3).

## 6. Dimensions

### 6.1 Declaring a dimension

A dimension is declared by a **dimension declaration**: the keyword
`dimension`, the name, an optional **member source**, and property lines.

```ebnf
dimension-declaration = "dimension", name, [ member-source ], line-end,
                        { property-line } ;
member-source         = "{", { nl }, [ name, { ",", { nl }, name } ], { nl }, "}"
                      | "from", string ;
```

```fml
dimension Region { North, South, East }          # members listed inline, in order

dimension Product from "dimensions/Product.csv"  # members in a member file (§6.4)
  @parent ProductGroup
  @attribute Color string
  @folder "Sales"

dimension Customer                               # members are data, not listed here
  @parent Segment
  @attribute Country string

dimension Scenario { Base, Upside, Downside }
  @rollup none                                   # never aggregated across
```

**[DIM-12] (member sources)**

- An **inline list** gives the members in order. It suits small dimensions
  without parents or attributes.
- **`from "<path>"`** names a member file, relative to the model directory
  (§6.4). The file MUST exist (`FML-E0612`).
- With **no source**, the declaration states only the dimension and its
  properties. Its members, with their parents and attribute values, are data
  that users or integrations write; the documents do not list them. This is
  enough for many dimensions, such as customers or employees.

An inline list has no columns for parents or attributes, so a dimension with a
`@parent` or `@attribute` property MUST NOT list its members inline
(`FML-E0613`). A dimension declaration MUST NOT name a system dimension (§6.7)
(`FML-E0207`).

**[DIM-13] (dimension properties)** A dimension declaration accepts these
properties. Each MAY be given once, except `@parent` and `@attribute`, which MAY
be given once per dimension and once per attribute name. A second `@parent`
naming the same dimension is an error (`FML-E0707`), whether or not its `many`
and `required` modifiers differ [PARENT-4].

| Property | Meaning |
|---|---|
| `@parent <Dimension>` | makes `<Dimension>` a parent of this dimension (§7). The member source holds each member's parent in a column named `<Dimension>`. A `@parent` naming the dimension itself declares a tree (§6.6). Two words MAY follow the dimension, in either order: `many` lets a member have several parents [PARENT-2], and `required` makes an empty parent cell an error [PARENT-3] |
| `@null` | the dimension has a NULL member (§6.5). Takes no value |
| `@attribute <name> <type>` | a column holding one value per member; `<type>` is `number`, `integer`, `boolean`, `string` or `date` |
| `@semantic time` | a time dimension (§6.9) |
| `@rollup none` | no read aggregates across this dimension. A read that would aggregate over its members, by any `@rollup`, is null and is reported (`FML-W1107`). A read at a single member is unaffected. Default: aggregation is allowed |
| `@folder <string>` | the folder of the dimension (§6.8) |
| `@desc <string>` | a description |

A dimension name follows the rules for names (§4.5). Dimension names and
variable names occupy separate namespaces, but authors SHOULD NOT give a
dimension and a variable the same name.

### 6.2 Dimension tables

Each non-system dimension is backed by a **dimension table** with one row per
member. A table has the following columns:

| Column | Cardinality | Meaning |
|---|---|---|
| **primary key** | exactly one | the member name; unique within the dimension |
| **description** | at most one | free text describing the member, shown in user interfaces |
| **order** | at most one | an integer defining the display order of members |
| **foreign key** | zero or more | one per `@parent` of this dimension (§7); each cell names zero, one or several members of the target dimension |
| **attribute** | zero or more | one per `@attribute` of this dimension; each cell holds a value of the attribute's type, or nothing |

A dimension table MAY additionally be placed in a **folder** for navigation in
user interfaces (§6.8). An engine MAY keep further columns per member; they are
described in its implementation profile.

### 6.3 Members

**[DIM-1]** Member names MUST be unique within their dimension, compared
case-insensitively (`FML-E0603`). The same name MAY occur in different
dimensions — `"01"`, for example, is a member of both `Months` and
`Year to date` — which is why member references in formulas are qualified by
their dimension (§10.4).

**[DIM-2]** A member referenced by a pinned grain entry (§8.4) or by a filter
in a formula (§10.4) MUST exist in its dimension when the model is validated
against an engine (`FML-E0302`). Tooling MUST NOT create a member because a
document names it.

Member names SHOULD be stable identifiers (codes) rather than labels; human
labels belong in the description column.

**[DIM-7]** Deleting a member that a formula names leaves that formula
referring to a member that does not exist [DIM-2]. What an engine that holds a
loaded model does with such a formula, and whether renaming a member there
carries its formulas along, is implementation-defined. Tooling SHOULD refuse,
or at least warn before, deleting a member that any formula references
(`FML-W0604`); authors SHOULD rename instead.

**[DIM-8]** A dimension table MUST contain at least one member other than its
NULL member. The order column is the display order (ascending); it does not
affect evaluation.

### 6.4 Member files

A **member file** holds the members of one dimension, with their descriptions,
parents and attribute values. The dimension's declaration names it
(`from "<path>"`, §6.1). The RECOMMENDED path is `dimensions/` followed by the
dimension name and `.csv`, with the characters `\ / : * ? " < > |` replaced by
`_`.

**[DIM-3]** A member file is a CSV file as RFC 4180 defines it, encoded in
UTF-8, so that spreadsheets, databases and data tools read it as it is:

1. The first line is the **header**; every further line is a **member row**.
   There are no comment lines and no blank lines.
2. Cells follow RFC 4180 quoting: a cell containing `,`, `"` or a line break is
   enclosed in double quotes, and a `"` inside it is doubled. Cells are not
   trimmed: spaces are part of the value.
3. The header's first cell is the **dimension name**, which MUST be the name of
   the declaration that names the file. It is followed by `@description`, if
   the file holds descriptions, and then by one cell for each `@parent` and each
   `@attribute` of the declaration, in any order.
4. A header cell holds a name as plain text, without the quotes of FML string
   form, and is compared with **exact case**. Every cell after the first and
   after `@description` MUST equal exactly one parent dimension or attribute
   name of the declaration, and every `@parent` and `@attribute` MUST have its
   cell (`FML-E0705`). An attribute MUST NOT share its name with a parent of the
   same dimension, or be named `@description` (`FML-E0614`).
5. A member row holds the member name, then one cell per header column. A
   parent cell names the parent member; with `@parent … many` it MAY name
   several, separated by `|` [PARENT-2]. An empty parent cell states no parent
   [PARENT-3]; with `@parent … required` it is an error. A member name used in
   a parent cell MUST NOT contain `|`.
6. An attribute cell holds a value of the attribute's type, or nothing: a
   number, `true` or `false`, any text, or an ISO 8601 date such as
   `2026-03-15`.

Example — the chart of accounts, declared

```fml
dimension Account from "dimensions/Account.csv"
  @parent BSLine many
  @parent PLLine
  @null
  @folder "Finance/Accounts"
```

with `dimensions/Account.csv`:

```text
Account,@description,PLLine,BSLine
4000,Sales of goods,Revenue,NULL (BSLine)
4100,Sales of services,Revenue,
5000,Cost of goods sold,Cost of sales,
1200,Receivables from customers,NULL (PLLine),Trade receivables
1210,Mixed-use receivable account,,Trade receivables|Other receivables
```

**[DIM-10] (member files, further rules)** The order of a member file's rows is
the order of the dimension's members (§6.2). Every member row has exactly as
many cells as the header (`FML-E0609`). A parent cell names members that exist
in the parent dimension (`FML-E0610`). A model MUST NOT contain two member
files for one dimension (`FML-E0611`). A member file MUST NOT list the NULL
member, which only `@null` declares (`FML-E0615`).

### 6.5 The NULL member

**[DIM-5]** A dimension declared **`@null`** has one more member, named exactly

```text
NULL (<DimensionName>)
```

— the literal text `NULL`, a space, an opening parenthesis, the dimension name,
and a closing parenthesis. Examples: `NULL (Account)`, `NULL (Cost Center)`.
`@null` is the only way to give a dimension a NULL member. A member source MUST
NOT list it (`FML-E0615`), and a processor MUST NOT add one to a dimension that
does not declare `@null`.

The NULL member is the **default parent**: a child member whose parent cell is
empty has the parent dimension's NULL member as its parent rather than nothing
[PARENT-3]. This makes unmapped data visible in reports (it aggregates under a
real member), keeps rollups complete, and gives data-quality checks a single
place to look. A healthy model has few or no members under NULL members.

A dimension that is the parent of a dimension whose members may be unmapped
SHOULD declare `@null` (`FML-W0606`). A child's members may be unmapped when
they are data (the child has no member source), or when its member source has
an empty cell in that parent's column; a parent declared `required` [PARENT-3]
and a tree are never unmapped. Three cases SHOULD NOT, or MAY not:

- **Time dimensions** have no NULL member.
- **Entity-style dimensions populated entirely by integration** (employees,
  positions, individual contracts) SHOULD NOT declare one, because a phantom
  member would distort counts.
- **Classifier and synthetic dimensions whose every child is mapped by
  construction** (statement groupings, adjustment types, matrix axes) MAY omit
  it.

The NULL member's own parents are the NULL members of those parents of its
dimension that declare `@null`; it has no other parent. In a tree (§6.6) it has
no parent within the tree.

Tooling MUST NOT infer a parent from two members having the same name in the
child and parent dimensions. An identity mapping MUST be written explicitly; a
member with an empty parent cell has the NULL member as its parent.

For a read through a parent of a member whose parent cell is empty, see
[EVAL-15]; for tests against the NULL member, see [EVAL-17].

### 6.6 Hierarchies

A dimension hierarchy is expressed in one of two ways.

1. **Levels as separate dimensions** (RECOMMENDED for reporting structures):
   each level is its own dimension, and each names the next with `@parent`.

   ```fml
   dimension Account from "dimensions/Account.csv"
     @parent PLLine
   dimension PLLine from "dimensions/PLLine.csv"
     @parent PLGroup
   ```

2. **A tree** (a *parent–child* hierarchy within one dimension): a dimension
   that is its own parent, where each member names its parent member in the
   same dimension.

   ```fml
   dimension OrgUnit from "dimensions/OrgUnit.csv"
     @parent OrgUnit
   ```

   A member that is the parent of other members is a **rollup node**.

Both forms aggregate correctly. They differ in one respect that matters for
calculations: a rollup node of a tree is itself a member that
can hold a cell. See [EVAL-16] and [EVAL-22], and Guide §3.6 for when to choose
which.

### 6.7 System dimensions

**[DIM-6]** Every model contains the **system dimensions** `YearMonth`,
`Years`, `Months`, `Quarters` and `Versions`. An engine MAY also provide
`Half years` and `Year to date`; a document that references either is portable
only to engines that provide it. System dimensions are created and managed by
the engine. A document MAY reference them; it MUST NOT attempt to create,
remove or modify their members or parents (`FML-E0602`).

| Dimension | Members | Kind | Notes |
|---|---|---|---|
| `YearMonth` | `"<yyyy>-<mm>"` — for example `"2026-01"`, `"2026-12"` (ISO 8601) | time | a calendar month; the time dimension of a planning variable |
| `Years` | `"<yyyy>"` — for example `"2025"`, `"2026"` (ISO 8601) | time | a calendar year |
| `Months` | `"01"` … `"12"` | time | the month of the year, without a year: a cycle of twelve |
| `Quarters` | `Q1` … `Q4` | reading level | parent of `Months` |
| `Half years` (optional) | `H1`, `H2` | reading level | parent of `Quarters` |
| `Year to date` (optional) | `"01"` … `"12"` | reading level | member `"k"` aggregates months `"01"` … `"k"` under the source's `@rollup` |
| `Versions` | `Actual`, `Plan`, and the further members the manifest lists (§5.7) | scenario | |

The members of `YearMonth`, `Years`, `Months` and `Year to date` are written
in the digits of ISO 8601 (`YYYY-MM`, `YYYY`, `MM`) and begin with a digit, so
they are written in string form [LEX-1]:
`YearMonth > "2026-03"`, `Years > "2026"`, `Months > "03"`.

**[DIM-9]** The members of `YearMonth` and of `Years` MUST each form a
contiguous sequence (no gaps: `"2024", "2026"` without `"2025"` is invalid,
`FML-E0605`), and `YearMonth` covers whole years of `Years`. Both are given by
the manifest's horizon (§5.7). Years are **calendar years**: a fiscal year that
starts in another month is implementation-defined (§2.3), and an engine that
offers one documents how it changes these parents, `Quarters`, `Year to date`,
`currentYear()` and [PROP-4].

The parents `YearMonth -> Years` and `YearMonth -> Months` are predefined:
each calendar month has its year and its month of the year as parents, so
`"2026-01"` has the parents `"2026"` and `"01"`. So are `Months -> Quarters`, and
`Quarters -> Half years` and `Months -> Year to date` where the engine provides
those dimensions. The last has several parents: each month `"j"` has the parents `"j"` …
`"12"`.

A **period of a year** is read as the intersection of `Years` with a reading
level or with `Months`: the first quarter of 2026 is `Years > "2026"` with
`Quarters > Q1`, March 2026 is `Years > "2026"` with `Months > "03"` (the same
cells as `YearMonth > "2026-03"`), and the year to March is `Years > "2026"`
with `Year to date > "03"`. A read at a reading level alone, without `Years`, spans
every year of the model. `@rollup` governs every such read [PROP-4]: a read at
`Year to date > "k"` sums `"01"` … `"k"` for `@rollup sum`, takes `"k"` for
`closing_state` and averages the existing months for `average`.

A model does not declare system dimensions, so it cannot add parents,
attributes or properties to them [DIM-12].

The **canonical time grain** of a planning variable is `Versions, YearMonth`
(§13.1).

### 6.8 Folders

Dimensions (by `@folder`, §6.1) and variables MAY be placed in **folders** for
navigation in user interfaces. A folder path is a sequence of folder names written joined by
`/` (§9.4.6). Folders have no effect on evaluation.

### 6.9 Time dimensions of a model

A model can add a time dimension of its own — days, weeks, trading days,
production shifts — by declaring a dimension **`@semantic time`**:

```fml
dimension Day from "dimensions/Day.csv"
  @semantic time
  @parent YearMonth
```

**[DIM-11] (declared time dimensions)** `@semantic time` makes a dimension a
time dimension. Its members, in the order of its member file
[DIM-10], are its periods; members SHOULD be named in the digits of ISO 8601
(`"2026-03-15"` for a day, `"2026-W11"` for a week). A declared time dimension
is a time dimension in every rule: a grain holds at most one time dimension
[VAR-9], the time-series functions run along it, one member per step
([FUN-6]), and `closing_state` and `beginning_state` choose its last or first
member [PROP-4]. It is not a cycle, it has no NULL member [DIM-5], and the
date context functions do not read it
(§12.5). A `@parent YearMonth` lets it aggregate to months, years and every
reading level by the ordinary rules of parents (§11.6).

## 7. Parents and the dimension graph

### 7.1 Syntax

A parent is declared by a `@parent` property of the **child** dimension; the
dimension it names is the **parent**. There is no other way to declare one.

```fml
dimension SKU from "dimensions/SKU.csv"
  @parent Product
dimension Account from "dimensions/Account.csv"
  @parent PLLine many            # an account MAY sit under several P&L lines
  @parent BSLine required        # every account MUST name a balance-sheet line
dimension Employee
  @parent CostCenter
dimension OrgUnit from "dimensions/OrgUnit.csv"
  @parent OrgUnit                # a tree: parent–child hierarchy
```

### 7.2 Meaning

**[PARENT-1]** `@parent P` on dimension `C` declares a foreign-key column on `C`
targeting `P`. For every member of `C`, that column names the parent member or
members in `P`. The property declares the *relationship*; the *mapping* of
individual members is data, held in the foreign-key column (§6.4).

A parent gives the engine a path along which data flows (§11.6):

- a variable whose grain contains `C` can be read by a consumer whose grain
  contains `P` instead — the child cells are aggregated into their parents;
- a filter on a member of `P` can be applied to a variable whose grain
  contains `C` (§11.8).

Parents compose. If `C` has the parent `P` and `P` has the parent `G`, `G` is
**reachable** from `C` through the **parent chain** `C -> P -> G`, and the same
aggregation and filtering apply along the chain.

### 7.3 Several parents

**[PARENT-2]** By default each member has at most one parent in each parent
dimension. With `@parent P many`, a foreign-key cell MAY name several parent
members; a child cell is then counted under **each** of its parents, so the
parents' totals overlap. This suits genuinely shared allocations and several
reporting views, such as a GL account that belongs to two P&L positions. A
member with several parents in a parent dimension declared without `many` is an
error (`FML-E0616`). Processors MUST preserve every parent of a member; dropping
all but one silently changes the model.

### 7.4 An empty foreign key routes to the NULL member

**[PARENT-4]** A parent exists only by its `@parent` property. Its column
follows [DIM-3] (`FML-E0705`). A parent whose column is empty in every row is
reported (`FML-W0703`). A dimension declaration MUST NOT contain more than
one `@parent` naming the same parent dimension (`FML-E0707`). This is an error
even when the declarations are identical; modifiers are neither merged nor
overridden.

**[PARENT-3]** By default a parent is optional: a member's foreign-key cell MAY
be empty. With `@parent P required`, every member MUST name a parent in `P`,
and an empty cell is an error (`FML-E0617`); a member whose parent is genuinely
unknown names `P`'s NULL member, where `P` declares `@null`. For a dimension
whose members are data, an engine checks this when members are written.

A child member whose foreign-key cell is empty has the parent
dimension's NULL member as its parent (§6.5) [EVAL-15]. Where the parent
dimension does not declare `@null`, it has **no** parent: its data is invisible
to every consumer that reads through the parent, and to every filter on the
parent dimension.

Consequently, adding a parent to a model is a two-part change: declaring the
`@parent`, and populating its column. A model between the two is not neutral:
every child sits in the NULL member, so a read at the NULL member returns the
whole total and every other parent member reads null. Populate the column, and
name the NULL member explicitly for parents that are genuinely unknown.

### 7.5 Graph well-formedness

The language permits any directed graph of parents, including several paths
between two dimensions. Linters SHOULD report (§15.3):

- **cycles** other than a tree (`FML-W0701`);
- **diamonds** — two distinct paths from one dimension to another
  (`FML-I0702`), because aggregation along the two paths may differ, and
  because a filter or projection across them is ambiguous;
- parents whose foreign-key column is entirely empty (`FML-W0703`).

## 8. Variables

### 8.1 Syntax

```ebnf
variable-declaration = name, { nl }, "{", grain, "}", { nl },
                       [ "=", formula ], line-end, { property-line } ;
grain       = [ grain-entry, { ",", grain-entry }, [ "," ] ] ;
grain-entry = name, [ "=", name ] ;
```

```fml
# Input variable: grain only
"Headcount IN" { CostCenter, Versions, YearMonth }

# Calculated variable: grain and formula
"Personnel Cost" { CostCenter, Versions, YearMonth } = "Headcount IN" * "Average Salary IN"

# With properties
"Personnel Cost Documented" { CostCenter, Versions, YearMonth } = "Headcount IN" * "Average Salary IN"
  @folder "Workforce/Calculation"
  @notes "Monthly personnel cost per cost centre"
  @readonly true

# Pinned member in the grain
"Opening Cash" { Entity, Versions, YearMonth = "2026-01" }
```

**[VAR-1]** For a variable *without* a formula, property lines MAY begin on the
same line as the closing `}`:

```fml
"Price IN" { Product, Versions, YearMonth } @rollup average
  @format number
```

For a variable *with* a formula, the formula MUST be followed by a line
terminator before any property line. (Text after a formula on the same line
is part of the formula.)

### 8.2 Names

**[VAR-2]** A variable name is a name (§4.5), unique across the model [DOC-1].
Variable names SHOULD follow the conventions of Guide §2. In particular, names
ending in ` IN` and ` OUT` (with a space) are conventional markers and are
written in string form.

### 8.3 Grain

The grain is the ordered list of dimensions inside the braces. It names at
least one dimension: a variable with an empty grain `{ }` is an extension
[EXT-1] (in Farseer, a *measure*, Annex D).

**[VAR-3]** A dimension MUST NOT appear more than once in a grain
(`FML-E0202`).

**[VAR-9] (one time dimension)** A grain MUST contain at most one time
dimension — `YearMonth`, `Years`, `Months` or a dimension declared
`@semantic time` (§6.9) (`FML-E0206`) — and MUST NOT
contain a reading level (`Quarters`, `Half years`, `Year to date`). The
time-series functions run along that dimension (§12.3). A variable that varies
by month carries `YearMonth`; one that varies only by year carries `Years`; a
seasonal profile, the same in every year, carries `Months`; a quantity that
varies by day carries a declared time dimension of days (§6.9).

**[VAR-3a]** A grain SHOULD NOT contain both a dimension and a dimension
reachable from it through parents (its *ancestor*), and SHOULD NOT contain two
dimensions that are connected to each other by parents, directly or through a
chain, while
both being reachable from a common third dimension (an *interconnected* pair).
The ancestor is already reachable from the grain, and an engine MAY reject
such a variable. Several dimensions that are all reachable from one common
dimension, with no parent among them — `Employee` and `CostCenter`, both reached
from `Position` — form a *conformed star* and are safe (Guide §3.7).

**[VAR-4]** The grain is a statement of **dimensionality**: the variable holds
at most one value per coordinate of its grain. It is not a statement of
**density**: most coordinates of a large grain hold no cell (§11.2).

The order of grain dimensions has no effect on evaluation. Authors SHOULD use
a consistent order: business dimensions first, from most to least specific,
followed by the time grain `Versions, YearMonth`.

### 8.4 Pinned members

A grain entry of the form `Dim = Member` **pins** the dimension to one member.

```fml
"Budget Opex" { Account, Versions = Budget, YearMonth }
```

**[VAR-5]** A pinned entry removes `Dim` from the variable's free grain and
places every cell of the variable on `Member`. It is a **write-side**
declaration only: it determines *where the variable's cells are written*, and
it does **not** filter what the formula reads. See [EVAL-18].

**[VAR-6]** `Dim = Member` is valid only in a grain. It MUST NOT appear inside a
formula (`FML-E0401`). To read a variable at one member inside a formula, use a
filter: `sum(Var, Dim > Member)` (§11.8).

**[VAR-7]** A grain SHOULD NOT pin members of two dimensions that are connected
by a parent (for example `{ Account = "4000", PLLine = Revenue }` where `Account` has
`@parent PLLine`). Pin only the child; the parent follows from the
foreign key. The double pin is ambiguous; a processor SHOULD warn
(`FML-W0203`), and an engine MAY reject it.

### 8.5 Input variables and entered values

A variable without a formula is an **input variable**. Its cells are written by
people (through input forms) or by integrations.

A calculated variable whose `@readonly` property is `false` MAY also accept
**entered values** in individual cells. Support for this is optional; an
engine that supports it follows [VAR-8], and a model that relies on it is
portable only to such engines.

**[VAR-8]** Where an entered value exists in a cell of a calculated variable,
the entered value is the value of that cell; the formula supplies the cells
that have no entered value.

## 9. Properties

### 9.1 Syntax

A property line follows a variable declaration (or appears in a defaults
block) and has the form `@name value`:

```ebnf
property-line  = "@", identifier, [ property-value ], line-end ;
                                             (* no value only for @null, DIM-13 *)
property-value = string | number | "true" | "false"
               | identifier, [ "(", balanced-text, ")" ]
               | name, identifier, { identifier }
                                           (* @attribute <name> <type>; @parent <dim> [many] [required] *)
               | object ;
object         = "{", { nl }, [ pair, { ( "," | nl ), { nl }, pair }, [ "," ] ], { nl }, "}" ;
pair           = ( identifier | string ), ":", ( string | number | identifier ) ;
```

Value kinds:

| Kind | Example |
|---|---|
| identifier | `@type number`, `@rollup closing_state` |
| number | `@decimals 0` |
| boolean | `@readonly true` |
| string | `@folder "P&L/Revenue"` |
| object | `@numberFormat { custom: true, formatString: "0.0%" }` |

**[PROP-1]** Property lines apply to the dimension or variable declaration that
immediately precedes them. A property line that follows no dimension or variable
declaration and is not inside a defaults block is an error (`FML-E0102`). A
dimension declaration takes the properties of [DIM-13]; this section describes
the properties of variables, and defaults blocks apply to variables only.

**[PROP-2]** Property names are single identifiers. A property MUST NOT be
given twice on one variable or dimension; if it is, processors MUST report
`FML-W0204` and use the last occurrence. On dimensions, `@parent` is keyed by
parent dimension and `@attribute` by attribute name [DIM-13]. Repeated
`@parent` targets are errors (`FML-E0707`) instead of warnings [PARENT-4].

### 9.2 Defaults blocks

A document usually groups its variables — the imports of a block, then its
plan inputs, then its outputs — and each group repeats the same properties. A
defaults block states them once for the group below it:

```fml
@defaults
  @folder "Import"
  @readonly true

"IMPORT Sales Volume" { Product, Versions, YearMonth }
"IMPORT Sales Price"  { Product, Versions, YearMonth }

@defaults
  @folder "Revenue"

"Volume IN" { Product, Versions, YearMonth }
"Revenue"   { Product, Versions, YearMonth } = "Volume IN" * "Price IN"
  @format currency
```

Here both `IMPORT` variables are read-only in `Import`; `"Volume IN"` and
`Revenue` are in `Revenue` and **not** read-only, because the second block
replaces the first.

**[PROP-3]** A defaults block begins with a line `@defaults` and continues with
property lines. A document may contain any number of them, anywhere a
top-level statement may stand. A block applies to every variable declaration
that follows it in the same document, up to the next defaults block:

1. **A property on the variable wins.** Each property in the block applies to
   a variable that does not set that property itself.
2. **A later block replaces the earlier one.** Blocks do not merge: a property
   the later block omits is no longer inherited.
3. **An empty block ends inheritance.** `@defaults` followed by no property
   lines leaves the declarations below it with nothing to inherit.
4. **Before the first block, nothing is inherited.**
5. **A block never reaches another document** [DOC-3].

| Property | Value | Default | Purpose |
|---|---|---|---|
| `@type` | `number` \| `integer` \| `string` \| `date` \| `boolean` | `number` | stored value kind |
| `@rollup` | §9.4.2 | `sum` | aggregation rule |
| `@format` | `number` \| `percentage` \| `currency` \| `date` | `number` | display format family |
| `@decimals` | integer ≥ 0 | `2` | displayed decimals |
| `@numberFormat` | object (§14) | — | full display format |
| `@folder` | string path | none (unstated, [PROP-10]) | navigation folder |
| `@desc` | string | empty | display label; see §9.4.7 |
| `@notes` | string | empty | documentation of the variable |
| `@readonly` | boolean | `false` | lock against entry |
| `@numberValidation` | `{ min: n, max: n }` | none | permitted value range for entry |

Engines may define further properties [EXT-1]. The Farseer properties
`@active`, `@useHierarchy`, `@optimizeCalculation`, `@calculateOnDemand`,
`@zConstraint` and `@topDownMapping` are documented in
its implementation profile (Annex D).

### 9.4 Standard properties

#### 9.4.1 `@type`

The kind of value stored in the variable's cells: `number` (decimal; the
default), `integer`, `string`, `date` (a date serial number, §13.4) or
`boolean`.

`@type` governs storage and validation of entered values. It is independent of
display (`@format`). An integer quantity SHOULD set both `@type integer` and a
zero-decimal display format.

#### 9.4.2 `@rollup`

How the variable's values combine when they are read at a coarser grain —
across members of a dimension the reader does not carry, from children to a
parent along a parent or a tree, and from months to quarters and years.

| Value | Aggregate | Typical use |
|---|---|---|
| `sum` | sum of the values | flows: revenue, cost, volume, cash movements |
| `average` (alias `avg`) | arithmetic mean of the existing values | rates, prices, percentages, ratios |
| `min`, `max` | extremum | limits, thresholds |
| `closing_state` (alias `last`) | the value of the **last** period — strictly: null when that period is empty | balances: cash, receivables, debt, headcount at period end |
| `beginning_state` (alias `first`) | the value of the **first** period — strictly: null when that period is empty | opening balances |
| `none` | no aggregation: the variable reads null at every coarser grain | values meaningful only at leaf level |

**[PROP-4]** For a read at a year, or at a quarter of a year, of a variable
held by `YearMonth`, `closing_state` yields the value of the last month of the period,
`beginning_state` the value of the first, and `sum` the total. The **source**
variable's rollup governs: a consumer cannot override it.

`closing_state` and `beginning_state` select the last or first period **along
time only** — along the variable's time dimension; along every other dimension
the values are summed.

**[PROP-4a] (several dimensions at once)** A read that aggregates over several
dimensions at once is one aggregation over the union of the source cells it
covers: `sum`, `average`, `min` and `max` are taken over all of those cells
together, `average` dividing by their number. For `closing_state` and
`beginning_state`, the last or first period of the period read, taken from the
calendar and not from where the data ends [EVAL-28], is read separately for
each combination of the other dimensions, and the values found there are
summed: a product with a value in December contributes it to the year, one
whose data ends in March contributes nothing. A balance therefore rolls up
from lines to groups and from entities to the group as a sum, and from months
to the year as its December (to a quarter as its last month).

**[PROP-5]** Processors MUST accept `last` as an alias of `closing_state` and
`first` as an alias of `beginning_state`, and MUST accept `avg` as an alias of
`average`. The hyphenated spellings `closing-state` and `beginning-state` are
not identifiers and MUST NOT be used.

There is no `count` rollup. Count with a 1-or-null presence flag and `sum`
(Guide §5.3). Engines may define further `@rollup` values [EXT-1]. Farseer's
`formula`, which recomputes a ratio from the totals at every coarser grain, is
documented in its implementation profile (Annex D).

#### 9.4.3 `@format` and `@decimals`

`@format` selects the display family: `number` (default), `percentage`,
`currency`, `date`. `@decimals` sets the number of decimals displayed. Both are
display-only and never change stored values.

**[PROP-6]** `@format` takes a bare keyword. A parenthesised argument such as
`currency(EUR)` is not part of FML and is an error (`FML-E0902`). Write `@format currency`, and give the currency code, where it
is not the engine default, in the `currency` field of `@numberFormat` (§14):

```fml
"Revenue OUT" { Product, Versions, YearMonth } = "Volume IN" * "Price IN"
  @format currency
  @numberFormat { currency: "EUR" }
  @readonly true
```

**[PROP-7]** A percentage variable holds the **ratio** (0.25 for 25 %). The
formula MUST NOT multiply by 100; the display applies the factor.

#### 9.4.4 `@numberFormat`

The complete display format as an object. See §14 for its fields and for the
rule that keeps `type` and `formatString` consistent.

#### 9.4.5 `@readonly`

`true` locks every cell of the variable against entry. **[PROP-8]** Every
variable that is not intended for planner entry SHOULD be `@readonly true`;
under the naming convention of Guide §2 this means every variable whose name does
not end in ` IN`.

#### 9.4.6 `@folder`

The navigation folder of the variable, as a path of folder names joined by `/`,
relative to the root of the variable tree. `"P&L/Revenue"` is the folder
`Revenue` inside the folder `P&L`.

**[PROP-9]** A folder *name* that itself contains `/` is written with the
escape `\/`, and a literal `\` in a name as `\\`. Inside an FML string the
backslash is itself escaped, so the source text is, for a folder named `R/E`
inside `Sub`:

```text
  @folder "Sub/R\\/E"
```

Empty segments and spaces around separators are ignored: `"A / B"`, `"A//B"`
and `"/A/B/"` all denote `A` → `B`.

**[PROP-10]** A variable without `@folder` has no stated folder: the absence
does not denote the root of the variable tree, and a processor MUST NOT emit a
root `@folder` for it.

#### 9.4.7 `@desc` and `@notes`

`@notes` holds documentation of the variable: what it represents, where its
data comes from, assumptions and owner. **Prose about a variable belongs in
`@notes`.**

`@desc` is a short **display label**. User interfaces may render it in place
of, or next to, the variable name — for example as a row label in a report.
**[PROP-11]** Authors SHOULD leave `@desc` empty on variables. A label is shown
in place of the name, so prose placed in `@desc` replaces the name wherever a
view shows labels; prose belongs in `@notes`.

#### 9.4.8 `@numberValidation`

`{ min: <number>, max: <number> }` — omit a bound to leave it open (FML has no
null literal; `null` would be read as an identifier) — the permitted range for
entered values. Has no effect on calculated values.

### 9.5 Unknown properties

**[PROP-12]** A processor MUST accept a property whose name it does not
recognise, MUST preserve its name and value across a round trip, and MUST NOT
treat it as an error. A linter MAY warn (`FML-I0901`). This allows engines to
introduce properties without a change to the grammar.

## 10. Formula expressions

The formula of a variable is an **expression**. This section defines its
syntax; Section 11 defines its meaning; Section 12 defines the functions it may
call.

### 10.1 Grammar

```ebnf
formula        = expression ;
expression     = term, { ( "+" | "-" ), term } ;
term           = factor, { ( "*" | "/" ), factor } ;
factor         = "-", factor | number | reference | call | "(", expression, ")" ;
reference      = name ;
call           = identifier, "(", [ argument, { ",", argument } ], ")" ;
argument       = member-ref | expression ;
member-ref     = name, ">", name ;
```

**[EXPR-1]** `*` and `/` bind more tightly than `+` and `-`. Operators of equal
precedence associate to the left: `A - B - C` is `(A - B) - C`, and `A / B * C`
is `(A / B) * C`. Parentheses override precedence.

**[EXPR-2]** There is no unary plus. A unary minus negates its operand and
binds more tightly than `*` and `/`: `-Revenue * Rate` is `(-Revenue) * Rate`.
It keeps the operand's cells: `-x` is null where `x` is null and `0 - x`
elsewhere, so `-Revenue` and `-(A + B)` place no cell that their operand does
not. A negative *literal* (`-1`) is always valid [LEX-5].

**[EXPR-3]** There are no infix comparison or logical operators. Comparisons
and logic are functions: `eq`, `gt`, `gte`, `lt`, `lte`, `and`, `or`, `not`
(§12.4). `A == B`, `A > B` (between two values), `A && B` are not FML.

**[EXPR-4]** There are no string literals in variable formulas. A double-quoted
token in a formula is a **name** (a variable, dimension or member), never text.

**[EXPR-5]** Parentheses in a formula MUST balance. A processor MUST reject a
formula whose parentheses do not balance — an unmatched `)`, or a `(` still open
at the end of the formula or of the document (`FML-E0103`) — and SHOULD reject one in which a continuation line inside an
open parenthesis begins with `@` or with a variable header, because that
pattern indicates a missing `)` that would otherwise absorb the following
declarations.

### 10.2 Operands

| Operand | Example | Meaning |
|---|---|---|
| number | `0.05`, `12`, `-1` | a constant |
| variable reference | `Revenue`, `"Volume IN"` | the referenced variable's value at the coordinate being evaluated (§11) |
| function call | `sum(Revenue, Region > North)` | §12 |
| parenthesised expression | `(A + B)` | grouping |

**[EXPR-6]** A variable reference is resolved against the variables of the
whole model [DOC-1]. A reference to an unknown name is an error at validation
(`FML-E0301`).

### 10.3 Where member references may appear

A **member reference** names one member of one dimension. It may appear only as
an argument of a function that accepts members: a filter of `sum` (§12.2),
the arguments of `hasDMember` (§12.4), and the member arguments of the
selectors (§12.6) `and`, `or`, `not`. It is not an operand of arithmetic.

### 10.4 Member reference forms

```text
Region > North                       # qualified: dimension > member
Region > "North America"             # quoted member
"Cost Center" > "CC 100"             # quoted dimension and member
Versions > Actual
```

**[EXPR-7]** A member reference MUST be **qualified** — written
`Dimension > Member` [EXPR-8]. In canonical form there is one space on each
side of `>`.

**[EXPR-8]** An **unqualified** member reference — a member name alone, as in
`hasDMember(Actual)` or `sum(X, Q1)` — MUST NOT appear in a conforming
document: every member reference is qualified by its dimension. An engine that
meets one MUST either reject it (`FML-E0402`) or resolve it only where the
name identifies exactly one member of the model; it MUST NOT ignore it. A
linter reports `FML-W0403`, and a processor MAY rewrite the reference to
qualified form when the member name is unambiguous in the model.

**[EXPR-9]** `Dim = Member` (with `=`) is grain syntax and MUST NOT appear in a
formula [VAR-6]. `Var { Dim = Member }` is not a formula operand.

> **Note — implementation detail.** Engines may store references in an internal
> identifier form. Such forms are not FML and MUST NOT appear in documents.

## 11. Evaluation semantics

This section is the heart of the specification. A model that is syntactically
valid can still be wrong by an exact multiple, read null where data plainly
exists, or materialise hundreds of millions of cells. Every one of those
failures is explained by a rule in this section.

### 11.1 The evaluation model

**[EVAL-1]** A formula is written once and holds at **every coordinate** of its
variable's grain. Conceptually, the engine evaluates the formula separately at
each coordinate, with that coordinate as the **evaluation context**. Every
operand is read *at* the context — that is, at the corresponding coordinate of
the operand's own grain (§11.4–§11.6).

**[EVAL-2]** Evaluation is **pure and deterministic**: the value of a cell is a
function only of the model — its documents, member files and manifest (§5.7) —
and its stored data. Evaluation order is derived from the dependency graph
(§11.11) and is not observable.

**[EVAL-2a] (two orders of aggregation)** Inside a formula, every operand is
first brought to the formula's grain — aggregated, projected or looked up
(§11.4–§11.6) — and only then is the operator applied: **aggregate, then
compute** [EVAL-8]. A variable read at a coarser coordinate than its own grain
is the aggregate, under its `@rollup`, of its own cells: **compute, then
aggregate**. `Margin = Profit / Revenue`, read at a year, is the rollup of the
monthly margins; a margin of the year's totals is a formula at `Years`.

### 11.2 Cells, null and zero

**[EVAL-3]** Storage is **sparse**. A coordinate either holds a cell with a
value, or holds nothing. "Holds nothing" is called **null**. Null is not a value
and in particular is not zero:

| | null | `0` |
|---|---|---|
| a cell | no | yes — a populated cell |
| meaning | no data here | the value here is exactly zero |
| in a `sum` rollup | contributes nothing | contributes 0, and counts as a populated cell |
| `x * …` | `x * null` is null | `x * 0` is `0` (a new cell) |

A conforming model returns null — not zero — wherever there is no data. A zero
is written only when zero is a real measurement (Guide §5).

### 11.3 Where cells come into existence

A formula does not produce a value at every coordinate of its grain. It produces
a cell only where its operands give it somewhere to put one.

Define, for a formula, the operands in **value position** and those in
**condition position**:

- An operand is in **condition position** if it occurs inside the first
  argument of `if`, or inside an argument of `hasDMember`, or inside a
  comparison, a boolean connective or `hasValue` that is itself in condition
  position.
- Every other operand is in **value position** — including the second and
  third arguments of `if`, the operands of arithmetic, the first argument of
  `sum` and of the time-series functions, and the operands of a comparison, a
  boolean connective or `hasValue` that is used in value position [EVAL-6].

**[EVAL-4] (the anchoring rule)** A formula creates a cell at a coordinate only
if at least one **variable reference in value position** has data that reaches
that coordinate. References in condition position contribute **no
coordinates**: they can remove cells (by making a branch null) but never add
them. **Literals contribute no coordinates.**

Consequences that follow directly, and are frequently mistaken for defects:

1. **A formula built only from literals creates no cells at all.**

   ```fml
   Probe { Region, Versions, YearMonth } = if(hasDMember(Region > North), 1, 2)
   # → no cells: nothing anchors a coordinate
   ```

2. **A default taken through `hasValue` does not widen the grid.**

   ```fml
   Weight { Position, Versions, YearMonth } = if(hasValue("Fraction IN"), "Fraction IN", 1)
   # → cells only where "Fraction IN" has data; the default 1 never appears
   ```

3. **A literal output gated on two or more variables creates no cells.**

   ```fml
   Ready { Entity, Versions, YearMonth } = if(and(eq(A, 1), eq(B, 1)), 1)
   # → no cells
   Ready { Entity, Versions, YearMonth } = if(and(eq(A, 1), eq(B, 1)), Carrier)
   # → cells where A = 1 and B = 1 (Carrier present)
   ```

4. **A condition removes cells from a wide product; it does not make it
   narrow.** Gating a dense product with `if(hasValue(…), …)` nulls the cells
   outside the gate, but an engine may still have to evaluate the whole
   product to find them. To keep the product narrow, multiply by a sparse
   carrier (Guide §5.5).

5. **A coarse fallback beside a full-grain operand never reaches the
   coordinates that operand lacks** [EVAL-4a] rule 1.

   ```fml
   # "List Price" { Item }; the other operands carry { Item, Versions, YearMonth }
   "Price eff" { Item, Versions, YearMonth } =
     "Set Price IN" + "Curve" * (1 - "Set Flag") + "List Price" * (1 - "Set Flag") * (1 - "Curve Flag")
   # → no cell for an item with neither a set price nor a curve: the list price
   #   is a value on the full-grain operands' cells, and they have none there
   ```

   Put the fallback where a full-grain operand has the cell — a carrier of the
   consumer, as in Guide §9.9 — or lift it to the consumer's grain first (Guide §4.4).

To give a formula the cell domain it needs, place a **carrier** — a variable
present exactly where cells should exist — in value position (Guide §5.4):

```fml
"Dense Anchor" { Position, Versions, YearMonth } = ("FTE IN" + "Salary IN") * 0 + 1
Weight       { Position, Versions, YearMonth } = if(hasValue("Fraction IN"), "Fraction IN", "Dense Anchor")
```

`A + B` has the **union** of the two operands' cells, and `* 0 + 1` turns every
value into 1, so `"Dense Anchor"` is 1 exactly where either input has data.

**[EVAL-4a] (full-grain references place the cells)** A value-position
reference **carries the whole output grain** when its variable's grain contains
every dimension of the output grain, each one directly or through a pin of the
output [VAR-5]. A dimension reached by projection [EVAL-13], lookup [EVAL-14]
or broadcast [EVAL-9] is not carried, and neither is a dimension that a filter
of an enclosing `sum` collapses to one member [EVAL-19] — `sum(X, D > m)` read
across `D` is a broadcast of one value. **The calendar is the exception:** a
reference held by `YearMonth` also carries `Years` and `Months`. Each calendar
month belongs to exactly one year and to one month of the year (§6.7), so read
at a year or at a month of the year it is aligned, as a pin would align it; a
yearly formula over monthly data has its cells where that data is. `Year to
date` is not carried: a month belongs to several of its members. A call of a time-series function
(§12.2, §12.3) counts as one value-position reference with the grain of its
first argument, whose cells are the cells the function produces by its
definition: `cumsum` carries forward, `delay` and `spread` move cells,
and `avg` in its default form has a cell in every period with a window.

1. If at least one value-position reference carries the whole output grain,
   **only those references place cells**: the candidate coordinates are the
   cells of those references, and every other operand only contributes a value
   there. This holds even when every such reference is empty — the formula
   then has no cells at all, whatever the other operands hold.
2. If no reference carries the whole output grain, each reference is read at
   **every member** of the output dimensions it lacks, and the candidate
   coordinates are all the coordinates so reached.

At each candidate coordinate the formula is evaluated by [EVAL-11]; a cell
exists where the result is not null.

```fml
# X { Versions, YearMonth } — full grain; Rate { YearMonth } — no Versions
T1 { Versions, YearMonth } = X + Rate
# → cells exactly where X has data; Rate adds its value there
# → no cells at all while X is empty, however much Rate holds

T2 { Versions, YearMonth } = 0 + Rate
# → no full-grain reference: Rate is read at every version,
#   and 0 + Rate is a value wherever Rate has one
```

Rule 1 is the source of most "missing data" reports: a lower-grain term next to
an **empty** full-grain term yields nothing, and the same term next to a
**populated** one adds normally. The constructs that follow — the merge of
[VER-4], [EVAL-6a], cross-grain addition [EVAL-12], lookups [EVAL-14] — are
applications of this rule, not separate mechanisms.

**[EVAL-5] (single-variable condition)** When the condition of an `if` that
is the whole formula references exactly **one** variable and both branches are
literals, an engine MUST infer the cell domain from that variable: `if(gt(X,
100), 1)` creates cells where `X > 100`; `if(gt(X, 100), 1, 0)` and
`if(hasValue(X), 1)` create cells on `X`'s cells. With two or more variables in the
condition it does not ([EVAL-4] consequence 3). Because adding a second variable
to such a condition silently removes every cell, authors SHOULD return a carrier
instead of a literal whenever the condition may later grow.

**[EVAL-6]** A **bare comparison** (a comparison used as the whole formula, or in
value position) is in value position and inherits the density of its operands:
it yields `1` or `0` wherever its operands have data, and nothing elsewhere.
`gt(X, 100)` over a dense `X` therefore writes a `0` into every cell where the
test is false. The same holds for `and`, `or` and `not` used in value position:
their operands then contribute coordinates as for a comparison. `hasValue(X)` in
value position is `1` where `X` has a cell and **null** elsewhere, never `0`:
`Carrier * hasValue(X)` is null where `X` is missing, `Carrier + hasValue(X)` is
`Carrier` there.

**[EVAL-6a] (broadcast by condition)** When no value-position reference of an
`if` carries the whole output grain — typically a version-free feeder under a
forecast flag that carries `Versions` — the branches are read at every member
of the missing dimensions [EVAL-4a] rule 2, and the condition decides which
coordinates hold a value. `if(eq("FC Actual Flag", 1), "Sales upstream")`
therefore has cells on every version and period where the flag is 1 and the
version-free feeder has data. The effect survives nesting: `0 + if(…)` has the
same cells, with `0` where the flag is not 1. It is lost as soon as the
enclosing expression has an operand that carries the whole grain, which then
places the cells alone [EVAL-4a] rule 1. The merge of [VER-4] and rule 3 of
[PERF-1] depend on it.

**[EVAL-6b] (inline branches)** An inline expression in a branch of an `if`
places cells exactly as the same expression stored as a variable would:
`if(hasValue(S), S, A + B)` has cells wherever `S`, `A` or `B` has data.
Storing `A + B` as its own variable is a matter of readability, not of
semantics.

### 11.4 Operand alignment

For an operand `V` read in a formula of variable `T`, compare the two grains.

**[EVAL-7] (shared dimensions align)** For every dimension present in both
`V`'s grain and `T`'s grain, `V` is read at the **same member** as the
evaluation context. Shared dimensions are never aggregated and never broadcast;
they are matched cell by cell.

**[EVAL-8] (pre-aggregation is per operand)** For every dimension in `V`'s grain
that is **not** in `T`'s grain and not connected to a dimension of `T`'s grain
by a parent chain in either direction (§7.2, §11.6), `V` is first
**aggregated** over that dimension using `V`'s own `@rollup`, and only then
combined with the other operands. This happens **independently for each
operand, before the operator is applied**.

**[EVAL-9] (broadcast)** For every dimension in `T`'s grain that is **not** in
`V`'s grain and not connected to a dimension of `V`'s grain by a parent chain in
either direction, `V` has the
**same value at every member** of that dimension.

Broadcast is legitimate when the same value is meant to apply to every member —
an exchange rate by period multiplied into an entity-level amount, an actual
without a version axis read by every version. It is a defect when it is not
meant (an **orphan dimension**, Guide §4.2).

Pre-aggregation has two consequences that the formula's surface does not show:

```fml
# Amount { Dim, Position, YearMonth } — 10 members of Dim
# Flag   { Dim }                          — 1 on 3 of the 10 members, null elsewhere
Target { YearMonth } = sum(Amount * Flag)
# → (Amount summed over all 10 members) × (Flag summed over Dim = 3)
# → NOT the sum of Amount over the 3 flagged members
```

```fml
# A flag cannot select a member of a dimension the result does not carry:
Selected { Position, YearMonth } = "Amount by Version" * "Role Budget Flag"
# → the all-version total: both operands are aggregated over Versions first
```

The remedy in both cases is an intermediate variable at the grain that still
carries the dimension (Guide §4.3).

**[EVAL-10]** A formula consisting of a **single reference** to a variable that
lacks a dimension of the output grain (`T { A, B } = V` where `V { A }`)
materialises a cell on every member of `B` wherever `V` has data, exactly like
`0 + V` and `V * 1` [EVAL-4a] rule 2. A document that wants the broadcast only
where something else exists combines the reference with a carrier that has the
target grain (Guide §5.4).

### 11.5 Arithmetic with null

**[EVAL-11] (null in arithmetic)** When all operands are aligned with the output
grain:

| Operation | Result |
|---|---|
| `a + b`, `a - b` | null if both are null; otherwise null operands count as 0 — a literal is never null, so `1 - x` is `1` where `x` is null |
| `a * b` | null if either is null |
| `a / b` | null if `b` is null or `0`; `0` if `a` is null and `b` is a value |
| any function of null | as stated per function (§12) |

**[EVAL-11a] (anchoring is decided by the whole formula)** Whether a cell
exists is decided once, for the whole formula, by [EVAL-4]. Inside a cell that
exists, sub-expressions are evaluated by [EVAL-11]: a factor such as
`(1 - "Set Flag")` is `1` where the flag is null, and does not null the product
it belongs to. The effective-price pattern of Guide §9.9 depends on this.

A null numerator does not null a quotient: `null / 2` is `0`, so
`"Annual Amount" * Share / 12` is `0` — a cell — where `Share` is null and the
cell is anchored by another operand. A zero divisor does: `x / 0` and
`x / null` are null, and so is every product that consumes them, while a sum
that consumes them takes its other operands [EVAL-11].

**[EVAL-12] (cross-grain addition takes the full-grain operand's cells)** An
operand of `+` or `-` that lacks a dimension of the output grain, or reaches it
by projection or lookup, is added normally — null counts as 0 [EVAL-11] — at
every coordinate the formula has. Which coordinates those are is decided by
[EVAL-4a]: where another operand carries the whole output grain, only that
operand's cells exist, so the lower-grain operand's value appears **only where
the full-grain operand has data**, and nowhere while it is empty.

```fml
# Actual { YearMonth } — no Versions;  Plan Export { Versions, YearMonth }
Merged { Versions, YearMonth } = Actual + "Plan Export"
# → Actual + Plan on every cell of Plan Export
# → nothing in a version, or in months, where Plan Export has no data
```

| Operator | Failure when grains differ | How it looks |
|---|---|---|
| `A * B` | silently **inflated** by a member count [EVAL-8] | a plausible number |
| `A + B` | the lower-grain operand **missing** wherever the full-grain operand has no cell | looks like missing data |

The remedy is a **projection**: an intermediate variable that holds the operand
at the consumer's grain (Guide §4.4), so that both operands place cells.

An operand that carries a dimension through a **pin** [VAR-5] is aligned on
that dimension: it holds its cells on the pinned member and is null on every
other member. A sum of such operands — a **collector**, each operand pinned to
a different member — is therefore aligned addition:

```fml
"Gross Pay" { Position, SalaryElement, Versions, YearMonth } =
  "EL101 Base Pay" + "EL102 Seniority" + "EL301 Year End Gift"
# each operand is pinned to its own SalaryElement member
```

**[EVAL-33] (numbers)** A value of `@type number` is a real number. An engine
computes with at least the precision and range of IEEE 754 binary64, rounding
to nearest; one that computes in decimal or with more precision documents it
(§2.3). A result that is not a finite number — an overflow, `power` of a
negative base to a fractional exponent, `power(0, e)` with `e` < 0 — is null.
In arithmetic and comparisons, `@type integer` and `date` values are numbers
and `boolean` values are `1` and `0`; a value computed into an `@type integer`
variable is stored rounded by `round` [FUN-7]. A `@type string` variable MUST
NOT be an operand of arithmetic or of a comparison (`FML-E0410`).

### 11.6 Reading through parents

Parents make dimensions *reachable* from one another (§7.2).

**[EVAL-13] (aggregation to a parent)** If `T`'s grain contains a dimension `P`
and an operand `V`'s grain contains a dimension `C` with a parent chain `C -> … ->
P`, then `V` is read at a member `p` of `P` as the aggregate, under `V`'s
`@rollup`, of `V` over all members of `C` that reach `p`. No `sum` is needed:

```fml
# Account is declared with @parent PLLine
"PL Plan at PLLine" { PLLine, CostCenter, Versions, YearMonth } = "PL Plan IN"
# "PL Plan IN" { Account, CostCenter, Versions, YearMonth }
# → each PLLine member receives the sum of its accounts
```

This is called a **projection**, and it is the only formula-level way to move
data between dimensions. Between dimensions with no FK path, no projection
exists; the relationship must first be modelled as a parent with data.

**[EVAL-14] (lookup from a parent)** If `T`'s grain contains `C` and an operand
`V`'s grain contains `P`, reachable from `C`, then `V` is read at a member `c`
of `C` as `V`'s value at the parent of `c` — or the sum over its parents, for a
multi-parent foreign key [PARENT-2]. Where another operand carries the whole
output grain, a lookup only supplies values to that operand's cells [EVAL-4a]
rule 1. Alone, it is read at every child: `T = V` has a cell on every child
whose parent has a value, and `0 + V` on every child, with `0` where the parent
is empty. To restrict a looked-up value to the children that hold data, combine
it with a carrier at the child grain.

**[EVAL-15]** A child member whose foreign key is empty reaches the parent
dimension's **NULL member** (§6.5): its data appears there in every projection,
and a lookup reads the NULL member's value for it. Without a NULL member in the
parent dimension it reaches nothing [PARENT-3]. In a tree an empty
parent makes the member a root, not a child of the NULL member.

**[EVAL-16] (rollup nodes)** In a tree (§6.6), a **calculated**
variable may hold a cell at a rollup node (a parent member) in addition to the
cells of the node's children. A **stored input** holds no cell at a rollup node
unless one was written there; whether an engine accepts an entry at the node
is implementation-defined, and an accepted entry writes one.

**[EVAL-17] (the NULL member through a parent)** The NULL member behaves like any
other member, through parents as well as at a variable's own grain:
`hasDMember(Target > "NULL (Target)")` evaluated across an FK holds for exactly
the rows whose key is empty or points at the NULL member [EVAL-15], and a read at
the NULL member returns their total. Where no row carries a key, every row is in
the NULL member and the read returns the whole total. Documents SHOULD still test positively for
the class of rows that should compute (Guide §3.8): a negative test against the NULL
member silently changes meaning as keys are populated.

### 11.7 Pinned grain members

**[EVAL-18] (a pin writes, it does not read)** In `T { D = m, … } = expr`, the
pin determines that `T`'s cells lie on member `m` of `D`. It applies **no
filter** to `expr`. Every operand of `expr` that carries `D` is read as though
`D` were absent from `T` — that is, aggregated over **all** members of `D`
[EVAL-8].

```fml
# Wrong — reads every member of PLLine, writes the total onto "Cost of sales"
"Cost of Sales Total" { PLLine = "Cost of sales", Versions, YearMonth } = "PL Amount"

# Right — the filter is where the reading happens
"Cost of Sales Total" { Versions, YearMonth } = sum("PL Amount", PLLine > "Cost of sales")
```

A pinned variable whose expression is an unfiltered aggregate of a variable
carrying the pinned dimension is almost always this mistake. Its result is
plausible — right sign, right order of magnitude — and wrong by the share that
the member represents of the whole.

**[EVAL-19] (a filter collapses only its own dimension)** In
`A * sum(B, D > m)`, the filter collapses `D` and nothing else. Every other
dimension that `A` and `B` share remains aligned cell by cell [EVAL-7]. If `A`
and `B` carry their values on different members of a shared, unfiltered
dimension, the product is null everywhere.

```fml
# Rate { PLLine, YearMonth }           — value on "Cost of sales"
# Vol  { PLLine, Region, YearMonth }   — value on "Revenue"
"Rate x Vol" { PLLine, YearMonth } = Rate * sum(Vol, Region > North)
# → null everywhere: PLLine stays aligned, and the two never meet
```

A **transfer variable** moves the value to the member where it is needed — the
deliberate use of [EVAL-18]:

```fml
"Vol at COGS" { PLLine = "Cost of sales", YearMonth } = sum(Vol, PLLine > Revenue, Region > North)
"Rate x Vol fixed" { PLLine, YearMonth } = Rate * "Vol at COGS"
# → correct, on "Cost of sales"
```

### 11.8 Filters

A **filter** is a member reference passed to `sum` (§12.2):
`sum(expr, Dim > Member, …)`.

**[EVAL-20] (filters are scopes, not predicates)** Each filter restricts the
cells of `expr` that are read to those on the named member, or reaching it
through parents. A filter MUST be a member reference (or a selector over
members); it MUST NOT be a condition — `sum(X, gt(F, 0))` is invalid
(`FML-E0404`). A filter MUST name a member, not a dimension — `sum(X, Region)`
is invalid (`FML-E0405`).

**[EVAL-21] (filters combine with AND)** Several filters intersect. Two filters
on **different members of the same dimension** select nothing — the result is
null, not the union. To read several members of one dimension, pass them as one
selector, `sum(X, or(D > a, D > b))`: the union is aggregated **once**, under
the source variable's `@rollup`. Adding separate `sum`s agrees with it only for
`@rollup sum` — for `average` over the values 1 and 3 the selector reads `2`,
the two sums `4`; `min` and `max` likewise read the extremum of the union.

**[EVAL-22] (subtree semantics)** `sum(X, D > m)`, where `m` has descendants in
a tree or through parents, includes the cell **on `m` itself plus**
the cells of all its descendants. Where `m` holds a cell of its own ([EVAL-16]),
that cell is counted in addition to its children.

**[EVAL-23] (own grain versus through a parent)** — the rule with the sharpest
consequences:

- A `sum` filtered on a dimension in the **consuming variable's own grain**
  **ignores the evaluation context** for that dimension and returns the full
  filtered total **at every member** of it.
- A `sum` filtered on a dimension **reached through a parent** from the consuming
  variable's grain **intersects** with the evaluation context and returns that
  cell's slice.

```fml
# PLLine is declared with @parent PLSection
# "PL Amount" { PLLine, YearMonth }

"Probe own" { PLLine, YearMonth } = sum("PL Amount", PLLine > "Cost of sales")
# → the cost-of-sales total, repeated on every PLLine member

"Probe fk"  { PLLine, YearMonth } = sum("PL Amount", PLSection > "Operating expenses")
# → each operating-expense line's own amount; no cell on other lines
```

Both behaviours are useful. The own-grain form is right for a
**denominator or broadcast** — every line's share of total revenue. The
through-parent form is right when each cell should receive **its own slice** and
the cells should add up to the total. Mixing the two forms in one formula is a
defect: the own-grain term is applied once per member that the through-parent
terms reach, and the result is wrong by an exact multiple of the own-grain term
(Guide §10, AP-01). Guide §3.4 gives the dimension design that avoids the problem.

### 11.9 Conditions and null

**[EVAL-24]** `if(c, a)` (two arguments) is `a` where `c` is true and null
elsewhere. `if(c, a, b)` (three arguments) is `a` where `c` is true and `b`
where `c` is false.

**[EVAL-25] (a null condition is false, and creates no cells)** Where `c` is
null — for example `hasValue(X)` where `X` has no cell — the condition reads as
false, and contributes no coordinates. Whether a cell exists is decided by the
value-position references of the branches [EVAL-4], [EVAL-4a]: at a coordinate
they anchor, `if(c, a, b)` yields `b`, literal included —
`if(hasValue(X), Carrier, 1)` is `1` where `X` is missing and `Carrier` has data.
At a coordinate nothing anchors there is no cell, so a literal else-branch is a
fallback only inside cells that a variable reference creates.

**[EVAL-26] (null operands of comparisons and connectives)** At a coordinate
where a cell exists:

- a comparison with **one** null operand reads it as `0`: `gt(5, null)` is `1`,
  `eq(null, 0)` is `1`;
- a comparison with **both** operands null is `0` (false), for every
  comparison: `eq(null, null)` is `0`, not `1`;
- `and` and `or` whose operands are all null are **null** — false as a
  condition, and null in value position (`Carrier * and(A, B)` has no value
  there); `not(null)` is `1`.

Documents that mean "missing" rather than "zero" MUST test it with `hasValue`
before comparing.

**[EVAL-27]** `if(c, 1, 0)` over operands that carry data yields `1` and `0`
values (it is not null where the condition is false), and therefore writes a
`0` into every cell where the condition is false and the operands have data
(Guide §5.2).

### 11.10 Time aggregation

**[EVAL-28]** A consumer whose time dimension is `Years`, or a read at a period
of a year (§6.7), of a variable held by `YearMonth` aggregates the months of
the period under the **source** variable's `@rollup` [PROP-4]: `sum` totals them, `closing_state` takes the last month of
the period, `beginning_state` the first, `average` the mean of the existing
values. `closing_state` and `beginning_state` read that month strictly: a year
whose December is empty reads null, even when earlier months hold values.

**[EVAL-28a] (coarser time read by a finer one)** A consumer held by
`YearMonth` that reads a variable held by `Years` reads, in each month, the
value of that month's year; one that reads a variable held by `Months` reads,
in each month, the value of that month of the year — a seasonal profile
repeats in every year. Both are lookups from a parent through the predefined
parents of `YearMonth` [EVAL-14], and [EVAL-28] is aggregation to a parent
[EVAL-13]: time follows the rules of every other dimension, with the one
exception of [EVAL-4a] — a monthly reference carries `Years` and `Months`, so
it places the cells of a formula held by either.

```fml
# Sales { Versions, YearMonth };  "Sales LY" { YearMonth } — no Versions
Delta { Versions, Years } = Sales - "Sales LY"
# → a cell in each version and year where Sales has data; "Sales LY" is read
#   in every version and adds its value there [EVAL-12]
# → no cell in a version or a year where only "Sales LY" has data
```

### 11.11 Dependencies and recalculation

**[EVAL-29]** The **dependency graph** has an edge from `V` to `T` whenever `T`'s
formula references `V`. The graph MUST be acyclic (`FML-E0501`). A recurrence —
a balance that depends on its own previous period — MUST be expressed with
`cumsum` (§12.3), not with a self-reference.

**[EVAL-30]** When stored data or the model changes, an engine recomputes every
dependent variable. Recomputation MAY be asynchronous; reads issued during it
MAY return earlier values.

**[EVAL-31] (dense cell production)** The **dense size** of a variable is the
product of the member counts of all dimensions in its grain. A sparse variable
with a large dense size is not a problem in itself. What fails is a formula
that **produces** cells densely at a scale the engine cannot hold. Such a
formula typically has no reference carrying the whole grain [EVAL-4a] rule 2,
adds a literal or a dense operand across an orphan dimension, or uses `avg` in
its default form (§12.2). An engine SHOULD estimate, before computing, how many
cells a formula can produce and report a formula above an
implementation-defined threshold; models MUST NOT be designed to produce dense
cells at that scale (Guide §8).

### 11.12 Time-series functions and expressions

**[EVAL-32]** When the first argument of a time-series function (`cumsum`,
`delay`, `spread`, `avg`) is an **expression** rather than a
single variable reference, its cells are those of the same function over the
expression stored as a variable: `cumsum(A - B)` and `cumsum("A minus B")` agree
cell for cell.

## 12. Function library

Every conforming engine provides the functions of this section. Function names
are **case-insensitive** (`SUM`, `Sum` and `sum` are the same function);
documents SHOULD write them in the case shown. An unknown function name is
rejected by an engine that does not implement it [EXT-2].
Functions beyond this section are extensions [EXT-1], [EXT-2].

For each function: **Syntax** gives the signature; **Requires** lists
dimensions that the variable's grain MUST contain; **Domain** states which
arguments are in value position for the anchoring rule [EVAL-4].

### 12.1 Mathematical functions

| Function | Syntax | Result |
|---|---|---|
| `round` | `round(x [, d])` | `x` rounded to `d` decimals (default 0) |
| `floor` | `floor(x)` | largest integer ≤ `x` |
| `ceil` | `ceil(x)` | smallest integer ≥ `x` |
| `abs` | `abs(x)` | absolute value |
| `power` | `power(base, exponent)` | `base` raised to `exponent` |
| `max` | `max(a, b)` | the larger of two values |
| `min` | `min(a, b)` | the smaller of two values |

Domain: all arguments are in value position. Null in, null out — except
`max` and `min`, which skip a null argument: `max(-5, null)` is `-5`,
`min(null, 3)` is `3`, and the result has a cell wherever either argument has
one.

`max` and `min` take exactly **two** arguments. They are not aggregations — use
`@rollup max` / `@rollup min` to aggregate.

**[FUN-7] (rounding)** `round(x, d)` rounds half **away from zero**, as
spreadsheets do: `round(2.5)` is `3`, `round(-2.5)` is `-3`. A negative `d`
rounds to tens, hundreds, …: `round(1234, -2)` is `1200`. `d` is rounded to a
whole number first. (`delay` rounds a fractional shift half towards +∞
instead, §12.3.)

```fml
"Net Revenue Floor" { Product, Versions, YearMonth } = max("Net Revenue", 0)
"Rounded FTE"       { CostCenter, Versions, YearMonth } = round("FTE IN", 1)
```

### 12.2 Aggregation

#### `sum`

**Syntax** `sum(expr)` · `sum(expr, filter1, filter2, …)`

**Result** The aggregate of `expr` over the cells selected by the filters,
intersected (AND), under the `@rollup` of the variable read: `sum` totals,
`average` means, `min`/`max` the extremum, and `closing_state` /
`beginning_state` take the last / first period along time and total along
every other dimension. Each filter is a member reference or a member selector
(`and`, `or`, `not` over member references). See §11.8 for the full semantics
— [EVAL-20] to [EVAL-23].

**Domain** `expr` is in value position. Filters are scopes and contribute no
coordinates.

```fml
"North Revenue"  { Product, Versions, YearMonth } = sum(Revenue, Region > North)
"Revenue Share"  { Region, Product, Versions, YearMonth } =
    if(gt(sum(Revenue, Region > Total), 0), Revenue / sum(Revenue, Region > Total))
"Group Result"   { Versions, YearMonth } =
    sum("Report Amount", and(Position > "Result", Scenario > "After adjustments"))
```

**[FUN-1]** `sum(X)` **without a filter** in a formula whose grain is reachable
from `X`'s is redundant — the projection of [EVAL-13] already aggregates. Write
`X`. `sum` is for filtered reads only: reading a variable at a coarser grain —
an intermediate product, a pinned grain [EVAL-18] — aggregates it as it is.

#### `avg` — moving average

**Syntax** `avg(expr, n)` · `avg(expr, n, skip_nulls)`

**Requires** a time dimension [FUN-6].

**Result** The average of `expr` over the `n` steps preceding the evaluation
period (the current period excluded); on `YearMonth` the window crosses year
boundaries, and `delay(avg(x, n), -1)` aligns it so that it ends with the
current period.

- By default a null period counts as `0` and the divisor is `n`. The
  result is a cell — possibly `0` — in **every** period of the horizon that has
  a window, which makes the default form dense over time (Guide §5, [EVAL-31]).
- With `skip_nulls` = `1` the divisor is the number of periods from the
  window's first period with data to its end — not the number of periods with
  data — and there are cells only where the window holds data.

`n` may be a number or a variable; if a variable, it MUST NOT have a time
dimension in its grain.

```fml
"Revenue Prior 3M Avg" { Product, Versions, YearMonth } = avg(Revenue, 3, 1)
"Revenue Trailing 3M"  { Product, Versions, YearMonth } = delay("Revenue Prior 3M Avg", -1)
```

`avg` is a **moving** average over time, not the arithmetic mean of its
arguments, and not an aggregation over a dimension (use `@rollup average`).

### 12.3 Accumulation and time shift

**[FUN-6] (along the time dimension)** The time-series functions — `cumsum`,
`delay`, `spread` and `avg` (§12.2) — run along the time dimension of the
variable that calls them [VAR-9], one **step** at a time:

| Time dimension | One step | At the ends |
|---|---|---|
| `YearMonth` | one calendar month; December is followed by January of the next year | the first and last month of the horizon (§5.7) |
| `Years` | one year | the first and last year of the horizon |
| `Months` | one month of the year, in a **cycle**: `"12"` is followed by `"01"` | none for a shift: `delay(x, 1)` at `"01"` reads `"12"`; `cumsum` starts at `"01"` and ends at `"12"` |
| a declared time dimension (§6.9) | the next member in member order | its first and last member |

A variable without a time dimension cannot call them (`FML-E0407`).

**[FUN-6a] (the edges of the horizon)** On `YearMonth` and `Years`, nothing
lies outside the horizon: `delay(x, n)` reads null in its first `n` periods; a
value that `delay` or `spread` would move past the last period is dropped;
`cumsum` starts in the first period from nothing (its previous value counts as
`0`); the window of `avg` holds only periods inside the horizon, its default
divisor stays `n`, and a period with no earlier period has no window and no
cell.

#### `cumsum`

**Syntax** `cumsum(expr)` · `cumsum(expr, factor)` · `cumsum(expr, factor, state)`

**Requires** a time dimension [FUN-6].

**Result** A running total forward through the timeline:

- `cumsum(x)`: `r(t) = r(t−1) + x(t)`.
- `cumsum(x, f)`: `r(t) = r(t−1) × (1 + f(t)) + x(t)` — compound accumulation.
  With `x` = 10 every period and `f` = 0.1: 10, 21, 33.1, 46.41, …
- `cumsum(x, f, s)`: as above, except that in any period where `s` has a value,
  the accumulation restarts from `s(t)`. Where `s` is null the series carries
  on.

A factor entered once keeps applying: where `f` is null, the last factor that
had a value is used, so a `0.5` entered in March compounds every later month.

**Domain** `expr`, `factor` and `state` are in value position, so
`cumsum(0, 0, S)` creates cells wherever `S` has data and carries them forward.
A series — one combination of the non-time dimensions — in which only `state`
has data still runs: `cumsum("Step", 0, "Reset")` carries the reset for an item
whose `"Step"` is empty. A carried total continues into later periods even
where `expr` is null. Where an engine supports entered values in a calculated
variable [VAR-8], a value entered in a period replaces the running total
there, and the accumulation continues from it.

```fml
Subscribers { PlanType, Versions, YearMonth } = cumsum("Net Adds")
  @rollup closing_state

"Loan Balance" { Loan, Versions, YearMonth } = cumsum("Loan Movement", "Monthly Rate IN")
  @rollup closing_state

# Carry a state value forward: restart wherever "Opening Balance" has a value
"Carried Opening" { Account, Versions, YearMonth } = cumsum(0, 0, "Opening Balance")
  @rollup closing_state
```

`cumsum` is the language's mechanism for **recurrences**: balances, stocks,
cumulative counts, carried prices. A balance variable SHOULD carry
`@rollup closing_state`.

#### `delay`

**Syntax** `delay(expr, n)`

**Requires** a time dimension [FUN-6].

**Result** `expr` shifted forward by `n` steps: the value at period `t`
appears at `t + n`. A negative `n` shifts backward. A fractional
shift is rounded to the nearest whole number, a half **upwards** (towards
+∞): `delay(x, 2.3)` shifts by 2, `delay(x, 2.5)` by 3, `delay(x, 0.7)` by 1,
`delay(x, -2.5)` by −2, `delay(x, -2.6)` by −3, `delay(x, -0.5)` by 0.

```text
Input:            2026-01=1  2026-02=2  2026-03=3  2026-04=4
delay(Input, 2):  2026-01=·  2026-02=·  2026-03=1  2026-04=2  2026-05=3  2026-06=4
```

```fml
Collections { Customer, Versions, YearMonth } = delay(Invoiced, "DSO Months IN")
```

**[FUN-2]** On `YearMonth`, `delay` carries values across year boundaries:
December of one year appears in January of the next, and `delay(x, 12)` reads
the same month of the previous year — for sparse sources as for dense ones. A null in January
after `delay(x, 1)` means that December holds no data, not that the shift
stopped at the boundary. A source whose December is genuinely empty — sparse
actuals, a balance entered only at year end — still needs an explicit anchor
where the January value must come from elsewhere.

#### `spread`

**Syntax** `spread(expr, n [, delay])`

**Requires** a time dimension [FUN-6].

**Result** Each value of `expr` distributed evenly over `n` steps, starting
`delay` steps later (default 0). Overlapping spreads add.

```text
spread(Input, 3, 1) with Input 2026-03 = 300:  2026-03=·  2026-04=100  2026-05=100  2026-06=100
```

```fml
Depreciation { AssetClass, Versions, YearMonth } = spread("Capex IN", 60, 1)
```

**[FUN-2a] (variable shifts and lengths)** The shift of `delay`, the length of
`spread` and the window of `avg` may be variables as well as
literals. A variable argument is read at the **source** period: `delay(x, s)`
moves the value of period `t` to `t + s(t)`, and a period whose shift is null
is dropped. An argument without a time dimension in its grain applies to every
period.

### 12.4 Logic and comparison

#### `if`

**Syntax** `if(condition, then)` · `if(condition, then, else)`

**Result** [EVAL-24], [EVAL-25]: `then` where the condition is true; `else`
(or null, with two arguments) where it is false. A **null** condition reads as
false and contributes no coordinates: the `else` branch applies at the
coordinates the branches anchor [EVAL-4].

**Domain** `condition` is in condition position; `then` and `else` are in value
position.

Valid conditions: a comparison, `hasValue`, `hasDMember`, a boolean connective
over these, or a value whose non-zero-ness is tested.

```fml
"Profit If Positive" { Entity, Versions, YearMonth } = if(gt(Revenue, Costs), Revenue - Costs)
Merged { Account, Versions, YearMonth } = if(hasDMember(Versions > Actual), "Actual Amount", "Plan Amount IN")
```

**[FUN-3]** The two-argument form is the default. A three-argument `if` whose
else-branch is a constant (`, 0)`) writes that constant into every cell where
the condition is false, and SHOULD NOT be used unless the constant is a real
value (Guide §5.2).

Both branches are evaluated over the whole timeline, and the condition picks
between them cell by cell: a time-series function inside a branch keeps running
through the periods where its branch is not picked. With `X` = 1, 10, 100, …
and a flag that is 1 in `"2026-01"`–`"2026-02"` and `"2026-05"`–`"2026-06"`,
`if(eq(Flag, 1), cumsum(X))` reads `11111` in `"2026-05"`, not `10011`.

Nested `if` is idiomatic for step tables and routers. The final, unmatched case
SHOULD be null, not `0`:

```fml
"Tenure Award" { Employee, Years } =
  if(eq("Tenure IN", 10), 300,
  if(eq("Tenure IN", 15), 360,
  if(eq("Tenure IN", 20), 420)))
```

#### Comparisons

| Function | True when |
|---|---|
| `eq(a, b)` | `a = b` |
| `gt(a, b)` | `a > b` |
| `gte(a, b)` | `a ≥ b` |
| `lt(a, b)` | `a < b` |
| `lte(a, b)` | `a ≤ b` |

Each takes exactly two arguments and yields `1` (true) or `0` (false). Null
operands: [EVAL-26]. In value position a comparison inherits its operands'
density [EVAL-6].

**[FUN-4]** Compare computed decimals after rounding, to avoid floating-point
noise: `eq(round(a, 2), round(b, 2))`.

#### Boolean connectives

| Function | True when |
|---|---|
| `and(c1, c2, …)` | every condition is true |
| `or(c1, c2, …)` | at least one condition is true |
| `not(c)` | the condition is false |

```fml
Eligible { Employee, Versions, YearMonth } =
  if(and(gt("Hours IN", 0), lte("Age IN", 65)), "Contracted FTE")
```

When their arguments are member references, the same three functions are
**member selectors** (§12.6).

#### `hasValue`

**Syntax** `hasValue(expr)` — true where `expr` has a cell. In condition
position a missing cell reads as false [EVAL-25]. In value position the result
is `1` where `expr` has a cell and **null** elsewhere, never `0` [EVAL-6].
**Domain:** condition position inside the condition of an `if`; value position
anywhere else (§11.3).

> **Caution.** `hasValue` cannot create cells. Where the tested variable is
> absent, an `if` takes its else-branch only at coordinates that some other
> value-position operand anchors [EVAL-4]. Never take a default through
> `hasValue` (§11.3, consequence 2).

#### `hasDMember`

**Syntax** `hasDMember(memberRef1, memberRef2, …)`

**Result** True where the evaluation context lies on **all** the named members —
directly, or through parents of the context's own members. False otherwise
(never null). **Domain:** condition position.

```fml
"Social Contributions" { Employee, Versions, YearMonth } =
  if(hasDMember(ContributionClass > Liable), "Gross Salary" * "Contribution Rate IN")
```

For tests against the NULL member, see [EVAL-17].

### 12.5 Date functions

Dates are **serial numbers** in the convention of common spreadsheet software:
serial 1 is 1900-01-01, serial 60 is that convention's fictitious 29 February
1900, serial 61 is 1900-03-01, and 2024-01-01 is 45292. Dates can be
compared, added and subtracted as numbers.

**Context functions** — no arguments; they describe the evaluation context's
period:

| Function | Result |
|---|---|
| `currentDate()` | serial number of the first day of the context's month |
| `currentMonth()` | month number, 1–12 |
| `currentYear()` | four-digit year |
| `daysInCurrentMonth()` | 28–31, leap-year aware |

**[FUN-8] (the period of a context function)** A variable that calls a context
function MUST carry, free or pinned, the dimension it reads its period from:
`YearMonth` for `currentDate()` and `daysInCurrentMonth()`; `YearMonth` or
`Months` for `currentMonth()`; `YearMonth` or `Years` for `currentYear()`
(`FML-E0407`). A dimension declared `@semantic time` (§6.9) is not one of
them.

**Manipulation functions:**

| Function | Result |
|---|---|
| `date(y, m, d)` | serial number of the date; each argument is rounded to a whole number, and a month or day outside its range rolls over (`date(2026, 13, 1)` is 1 January 2027, `date(2026, 3, 0)` is 28 February 2026) |
| `edate(date, months)` | the date shifted by whole months |
| `year(date)`, `month(date)`, `day(date)` | the component |

**[FUN-5] (null arguments of date functions)** A function of a date returns
null for a null date: `year(null)`, `month(null)`, `day(null)` and
`edate(null, n)` are null. `date()` reads a null argument as `0`
(`date(2026, null, 15)` is 15 December 2025). Documents SHOULD test a date that
may be missing with `hasValue` before taking it apart.

```fml
"Active Flag" { Employee, Versions, YearMonth } =
  if(and(gte(currentDate(), "Start Date IN"), lt(currentDate(), "End Date IN")), "Employee Anchor")

"Daily Cost" { Contract, Versions, YearMonth } = "Daily Rate IN" * daysInCurrentMonth()
```

For an open-ended contract (no end date), use an effective end date anchored on
the start date, as in Guide §9.7.

> **Note.** Context functions are not variable references; they contribute no
> coordinates [EVAL-4]. A formula whose only value-position operands are
> context functions and literals creates no cells. Pair them with a carrier, as
> `"Employee Anchor"` above.

### 12.6 Member selectors

As a filter of `sum`, the functions `or`, `and` and `not` combine
**members**:

```text
or(Region > East, Region > Adriatic)          # either member
and(Tier > Premium, Status > Active)          # both (members of different dimensions)
not(Lifecycle > Discontinued)                 # any member but this one
```

`not(D > m)` matches every other member of `D`, its NULL member included, and
excludes `m` with its whole subtree in a tree [EVAL-22].
Member arguments MUST be qualified
(`or(Region > East, Region > Adriatic)`) [EXPR-8].

## 13. Time and versions

### 13.1 The time grain

Time in FML is represented by system dimensions (§6.7). The RECOMMENDED grain
for any quantity that varies by period and scenario is

```text
{ <business dimensions>, Versions, YearMonth }
```

A **period** is a member of `YearMonth`, such as `"2026-03"`. A grain holds one
time dimension [VAR-9], and the time-series functions run along it [FUN-6].
Quarterly and annual figures are not stored: they are read at `Years`, or at a
period of a year — `Years` with `Quarters`, `Half years`, `Months` or
`Year to date` — under the variable's `@rollup` [EVAL-28].

Quantities that do not vary by month carry `Years` instead (an annual
assumption `{ Grade, Versions, Years }`); a seasonal profile that is the same
in every year carries `Months` (`{ Product, Months }`); quantities that do not
vary in time carry no time dimension. A coarser time grain is looked up in the
months where it is read [EVAL-28a].

Monthly grain is the practical floor. Daily or transaction-level grains SHOULD
be aggregated to months before they enter the model (Guide §8).

### 13.2 Flow and balance quantities

| Kind | Examples | `@rollup` | Year value |
|---|---|---|---|
| flow | revenue, cost, cash movements, hires | `sum` | total of the months |
| balance | cash, receivables, debt, headcount, inventory | `closing_state` | value of the last month |
| opening balance | opening equity, opening debt | `beginning_state` | value of the first month |
| rate, price, percentage | price, FX rate, margin %, growth % | `average`; a ratio recomputed from totals: Farseer's `formula` (Annex D) | mean of the months |

**[TIME-1]** A balance MUST NOT use `@rollup sum`: twelve monthly balances
summed is not a balance.

### 13.3 Versions

`Versions` is the scenario axis. `Actual` holds realised figures; `Plan`,
`Budget`, `Forecast` and other members hold planned figures.

**[TIME-2]** Imported actuals SHOULD NOT carry `Versions` in their grain. An
actual is a fact, not a scenario; a version-free actual is broadcast to every
version that reads it [EVAL-9], which is exactly what a rolling forecast needs.

**[TIME-3]** Formulas SHOULD refer to the `Versions` dimension only through
`Versions > Actual`. Which version a calculation applies to is controlled by
**data** — for example a per-version flag input marking which periods are
actuals — never by naming plan versions in formulas. A scenario is a `Versions`
member plus the assumption inputs that differ in it.

Guide §6 develops these rules into the forecasting pattern.

### 13.4 Dates

Date-valued variables (`@type date`, `@format date`) hold serial numbers
(§12.5). Contract start and end dates, hire and leave dates are typical inputs;
the date context functions turn them into period flags.

## 14. Number formats

Display formatting is carried by the `@numberFormat` object, which `@format`
and `@decimals` set in part.

### 14.1 Fields

| Field | Values | Default | Meaning |
|---|---|---|---|
| `type` | `NUMBER` \| `PERCENTAGE` \| `CURRENCY` \| `DATE` | `NUMBER` | format family |
| `decimals` | integer ≥ 0 | `2` | decimals shown |
| `formatString` | spreadsheet-style pattern | derived (§14.2) | the pattern actually used for display |
| `custom` | boolean | `false` | `true` when `formatString` is authored rather than derived |
| `currency` | ISO 4217 code | implementation-defined | currency symbol for `CURRENCY` |

**[FMT-2]** An implementation profile MAY define further fields — a display
scale, a style for negative numbers, a favourable direction. A processor MUST
preserve a field it does not recognise, as it does an unknown property
[PROP-12].

### 14.2 Keeping `type` and `formatString` consistent

**[FMT-1]** The display uses `formatString`; `type` names the format family.
An engine need not recompute one from the other. Whenever `@format` or `@decimals` changes, a processor MUST
recompute `formatString` from (`type`, `decimals`) unless `custom` is `true`:

```text
decimalPart = decimals > 0 ? "." + "0" × decimals : ""
NUMBER, CURRENCY  →  "#,##0" + decimalPart
PERCENTAGE        →  "#,##0" + decimalPart + "%"
DATE              →  ""
```

`@format percentage` with `@decimals 0` therefore yields `#,##0%`, whichever
order the two properties are written in.

A `PERCENTAGE` variable whose `formatString` lacks `%` displays 0.15 instead
of 15 %, without any error. A conforming processor SHOULD report
type/format-string disagreement (`FML-W1401`).

### 14.3 Custom and conditional formats

A custom format is authored as an explicit object, with `custom: true`. Format
strings follow spreadsheet conventions, including conditional sections:

```fml
"BS Control" { Entity, Versions, YearMonth } = "BS Assets" - "BS Equity and Liabilities"
  @numberFormat { type: NUMBER, custom: true, decimals: 0, formatString: "[=0]\"OK\";[<0]0 \"short\";0 \"over\"" }
```

When an object is given, the processor MUST NOT alter its fields; the author is
responsible for their consistency.

## 15. Static validation and diagnostics

### 15.1 Two stages

Validation happens in two stages.

| Stage | Input | Detects |
|---|---|---|
| **Local** (processor, linter) | the documents and member files only | syntax errors, duplicate names, grain errors, convention violations, graph shape |
| **Model** (engine) | the documents against an engine's dimensions, members and data | unknown variables and members, formula errors, engine limits |

A local processor cannot know every member of an engine's dimensions; it MUST
NOT report an unknown member as an error unless the member files are declared
complete.

### 15.2 Severity

Every diagnostic has a code (Annex C) and a severity:

- **Error** (`E`) — the document is not conforming, or the model cannot be
  loaded or evaluated as written.
- **Warning** (`W`) — the document is conforming but very likely wrong, slow
  or unsafe.
- **Information** (`I`) — a convention or style suggestion.

### 15.3 What a linter checks

At minimum, a conforming linter checks:

1. every syntax rule of Sections 4–10;
2. uniqueness of variable names [DOC-1] and of grain dimensions [VAR-3];
3. property value domains (§9.3);
4. the naming conventions of Guide §2.1 (mandatory rules), under the profile;
5. `@readonly true` on every variable that is not a planner input [PROP-8];
6. the dimension graph rules of §7.5;
7. the formula rules that can be checked syntactically: `Dim = Member` in a
   formula [VAR-6], unqualified member references [EXPR-8], a predicate as a
   `sum` filter [EVAL-20], a literal-only formula [EVAL-4], a three-argument
   `if` with a constant else-branch [FUN-3], `sum` without a filter around a
   single reference [FUN-1], `@rollup sum` on a variable named or noted
   as a balance [TIME-1];
8. on request, every use of an extension it recognises [EXT-3].

When the grains of operands are known, a linter SHOULD additionally check grain
alignment (Guide §4.5): orphan output dimensions, cross-grain addition, products of
operands at different grains inside `sum`, and pinned variables whose
expression reads the pinned dimension unfiltered.

### 15.4 Profiles

A linter runs under a declared **profile** that sets severities.

| Check | `lenient` | `standard` | `strict` |
|---|---|---|---|
| syntax and model errors | E | E | E |
| unknown variable or member (model stage) | E | E | E |
| naming rules (Guide §2.1) | I | W | W |
| `@readonly` on non-inputs | I | W | E |
| `@desc` set on a variable | — | I | W |
| parent cycles | I | W | E |
| diamonds | — | I | W |
| grain alignment (Guide §4.5) | I | W | E |
| sparsity rules (Guide §5) | I | W | E |
| extensions used [EXT-3] | — | — | I |
| missing `@notes` | — | I | W |

`standard` is the RECOMMENDED default during model development; `strict` is
RECOMMENDED as the acceptance gate before a model goes into production use.

## Annex A — Grammar (normative)

### A.1 Notation

The grammar uses ISO/IEC 14977 EBNF with these conventions: `=` defines,
`,` concatenates, `|` separates alternatives, `[ … ]` is optional, `{ … }`
repeats zero or more times, `( … )` groups, `"…"` is a terminal, `(* … *)` is
a comment, `;` ends a rule. Productions in *lexical* sections operate on
characters; the others operate on tokens, with whitespace and comments between
tokens ignored except where line terminators are significant.

The same grammar is available as a file: [`grammar/fml.ebnf`](../grammar/fml.ebnf).

### A.2 Lexical grammar

```ebnf
(* ---------- characters ---------- *)
letter        = "A" | … | "Z" | "a" | … | "z" ;
digit         = "0" | … | "9" ;
nl            = [ CR ], LF ;                      (* line terminator *)
ws            = " " | TAB ;

(* ---------- comments ---------- *)
comment       = ( "#" | "//" ), { any-char - nl } ;

(* ---------- tokens ---------- *)
identifier    = ( letter | "_" ), { letter | digit | "_" } ;
string        = '"', { string-char | escape }, '"' ;
string-char   = any-char - ( '"' | "\" | nl ) ;
escape        = "\", ( '"' | "\" | "n" | "t" | "r" | any-char ) ;
                                                  (* unknown escapes keep both characters, LEX-4 *)
number        = [ "-" ], digit, { digit }, [ ".", digit, { digit } ] ;
                                                  (* "-" binds only when immediately followed by a digit, LEX-5 *)
punctuator    = "{" | "}" | "(" | ")" | "," | "=" | ":" | "@" | ">" | "->" ;
operator      = "+" | "-" | "*" | "/" ;
```

### A.3 Document grammar

```ebnf
document          = { statement | nl } ;

statement         = dimension-declaration | defaults-block | variable-declaration ;

dimension-declaration
                  = "dimension", name, [ member-source ], line-end,
                    { property-line } ;           (* dimension properties: DIM-13 *)
member-source     = "{", { nl }, [ name, { ",", { nl }, name } ], { nl }, "}"
                  | "from", string ;

defaults-block    = "@", "defaults", nl, { { nl }, property-line } ;
                                                  (* applies to the declarations below it, up to the next block, PROP-3 *)

variable-declaration
                  = name, { nl }, "{", grain, "}",
                    ( { nl }, "=", formula, line-end, { property-line }
                    | inline-properties
                    | line-end, { property-line } ) ;
                                                  (* VAR-1: inline properties only without a formula *)
inline-properties = property, line-end, { property-line } ;

grain             = { nl }, [ grain-entry, { ",", { nl }, grain-entry }, [ ",", { nl } ] ], { nl } ;
grain-entry       = name, [ "=", name ] ;

property-line     = { nl }, property, line-end ;
property          = "@", identifier, [ property-value ] ;
                                                  (* no value only for @null, DIM-13 *)
property-value    = string
                  | number
                  | "true" | "false"
                  | identifier, [ "(", balanced-tokens, ")" ]
                  | name, identifier, { identifier }
                                                  (* @attribute <name> <type>; @parent <dim> [many] [required] *)
                  | object ;
object            = "{", { nl },
                    [ pair, { ( "," | nl ), { nl }, pair }, [ "," ] ],
                    { nl }, "}" ;
pair              = ( identifier | string ), ":", ( string | number | identifier ) ;

name              = identifier | string ;
line-end          = nl | EOF ;
```

### A.4 Formula grammar

```ebnf
formula           = expression ;                  (* continuation rules: §4.9, LEX-6 *)
expression        = term, { ( "+" | "-" ), term } ;
term              = factor, { ( "*" | "/" ), factor } ;
factor            = "-", factor
                  | number
                  | reference
                  | call
                  | "(", expression, ")" ;
reference         = name ;
call              = identifier, "(", [ argument, { ",", argument } ], ")" ;
argument          = member-ref | expression ;
member-ref        = name, ">", name ;
```

### A.5 Member file grammar

```ebnf
member-file       = header, { member-row } ;          (* RFC 4180, UTF-8; no comments,
                                                         no blank lines, DIM-3 *)
header            = csv-cell, { ",", csv-cell }, nl ; (* the dimension name, then
                                                         "@description", then parent
                                                         dimensions and attributes *)
member-row        = csv-cell, { ",", csv-cell }, nl ;
csv-cell          = quoted-cell | plain-cell ;
quoted-cell       = '"', { any-char - '"' | '""' }, '"' ;
plain-cell        = { any-char - ( "," | '"' | CR | LF ) } ;
fk-cell-value     = [ member-name, { "|", member-name } ] ;
member-name       = { any-char - "|" } ;
```

## Annex E — FML for spreadsheet modelers (informative)

| In a spreadsheet… | In FML… |
|---|---|
| a formula is copied into many cells | a formula is written once per variable and holds at every coordinate |
| rows and columns are positions | dimensions are named axes; positions do not exist |
| a subtotal row adds the rows above it | a subtotal is an aggregation along a parent — not written |
| an empty cell and a zero look alike | null and zero are different; null is free, zero is a cell |
| `SUMIF` over a range always has somewhere to write | a formula creates cells only where an operand has data [EVAL-4] |
| a lookup table is a range | a mapping is a parent with foreign-key data |
| a scenario is a copied sheet | a scenario is a `Versions` member |
| a quarter column sums three months | quarters and years are aggregations under `@rollup` |
| a balance is carried with `=previous + movement` | a balance is `cumsum(movement)` with `@rollup closing_state` |
| a hard-coded row reference picks a line | a classifier or synthetic dimension selects lines |
| a parent row is just another row | in a tree a parent member can hold a cell of its own [EVAL-16] |

## Annex F — Complete example model (informative)
A small but complete three-statement planning model for a fictitious trading
company. It demonstrates, in one place, the patterns of the Modelling Guide: a chart of
accounts whose parents are flat P&L lines and balance-sheet lines in a group
tree; version-free actuals merged with the plan by a forecast flag;
driver-based revenue, personnel, depreciation and financing; pinned transfer
variables collected onto accounts; P&L subtotals filtered through a parent; a plan
balance sheet in which every balance is a cumulative trail and cash is the trail
of the indirect cash flow, so that the balance sheet balances by construction;
and an identity control. The balance sheet balances by construction because
`delay` carries values across year boundaries [FUN-2]; `"CHECK BS FINAL"`
detects any case where it does not.

The same files are in [`examples/three-statement/`](../examples/three-statement/).
Every property is stated on each variable rather than through defaults blocks,
as in canonical form (§5.6). Its translation into a workbook (the FML to Excel
Translation companion) has been evaluated with the sample data of
`examples/three-statement/excel/`: every hand-computed value matches,
total assets and total equity and liabilities are both 4 510.8 at `2027-01`,
`"CHECK BS A"` is `0` in every period and `"CHECK BS FINAL"` has no cells. With a
horizon past 2027, `"Interest Expense"` holds `0`, not null, where
`"Interest Rate IN"` is empty: a null numerator over `12` is `0` [EVAL-11].

**Extensions:** none — the model is standard FML [EXT-3]. `"Gross Margin Pct"`
is a monthly ratio with `@rollup none`: FML has no standard rollup that
recomputes a ratio from the totals (Guide §9.2).
**Storage convention:** all-positive (Guide §9.1). **Naming:** Style A (Guide §2.2).
**Plan start:** the month after the opening month in which `"Opening Balances IN"`
is entered; all plan inputs are empty in the opening month.
